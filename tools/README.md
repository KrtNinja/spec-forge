# Проверка JavaScript-кода

Проверки предназначены для разработчиков Spec Forge. Они не добавляют инструкции
в контекст модели, которая составляет требования. Пользователю расширения
не требуется устанавливать npm-пакеты. Манифест, lock-файл, конфигурация ESLint
и зависимости разработки находятся только в `tools/`.

## Ревью изменений

[Скилл ревью](review-spec-forge/SKILL.md) для разработчиков: попросите проверить по нему PR, указанные файлы или переданный код. Результат — отчёт владельцу; собственных скриптов и автоматических исправлений нет.

## Локальный запуск

Нужны Git и Node.js 22.5.1. Все проверки используют эту версию.

Из корня репозитория:

```sh
cd tools
npm ci --ignore-scripts
npm test
npm run check
npm run coverage
```

Проверяются добавленные в Git файлы `.js`, `.mjs` и `.cjs` во всём репозитории.
Отчёты `coverage/` и `reports/` создаются в корне репозитория.
Из корня также можно запускать `npm --prefix tools test` и остальные команды.
Перед локальной проверкой новых файлов выполните `git add`.
Тесты называются `*.test.js`, `*.test.mjs`, `*.test.cjs` (также поддерживается `.spec`).
Каталог `tests/` предназначен для тестов и их вспомогательных файлов.

## Критерии продукта

Критерии меняются только в PR критериев; порядок работы — в [AGENTS.md](../AGENTS.md).

- `server/contract.mjs` — договор: описание и схема инструмента `spec_forge`, форматы документов задачи.
- `server/texts.mjs` — все тексты ответов пользователю. Тексты ответов пишутся только здесь; автоматически это не проверяется, владелец смотрит код в PR.
- `rules/` и `skills/` — готовые тексты правил и скиллов, которые согласуются с владельцем в PR критериев. PR реализации их не переписывает. Содержание проверяет владелец; автоматические проверки формата и размера не доказывают правильность инструкций.
- `tests/mcp/<группа>/<случай>/` — случаи вызова `spec_forge`. Группа — действие (`status`, `check`, `link`) или `common` для случаев, общих для всех действий.
- `tests/mcp.test.mjs` — общий тест случаев. Новый случай — новая папка, без нового кода.
- `tests/protocol.test.mjs` — обмен с сервером по MCP.
- `tests/extension.test.mjs` — манифест, правила, состав `server/`.

Папка случая:
- `input.json` — `when` (одна строка «Когда»), `refs` (номера FR или разделы устройства), `call` (аргументы вызова `spec_forge`);
- `expected.md` — точный текст ответа или `error.md` — точный текст ответа, когда вызов не удался (`isError`). Ошибки, найденные `check` в документах, — это успешный вызов. Последний перенос строки файла не учитывается. Метка `{сегодня}` заменяется сегодняшней датой `ГГГГ-ММ-ДД` по часам компьютера — для строки одобрения;
- `before/` — документы до вызова, если они нужны. Это корень проекта, в котором запускается сервер;
- `after/` — документы после вызова, только если вызов их меняет. Без `after/` документы остаются как в `before/`.

Git не меняет переводы строк в `tests/mcp/` (`.gitattributes`): случай с переводами строк CRLF остаётся таким на любой системе.

Правила случаев:
- в `before/` только документы, нужные случаю, и только нужное в них содержимое;
- ошибки одного документа проверяются одним случаем;
- общих заготовок, от которых случаи наследуют файлы, нет;
- режима перезаписи образцов по фактическому ответу нет.

## В каждом PR

- Тесты на Node.js 22.5.1. Ошибка теста завершает проверку неуспешно.
- ESLint: ошибки кода, неиспользуемые переменные, вложенность и сложность функций.
  Сложность функции должна быть меньше 10, вложенность — не больше 4.
  Файл — не больше 350 строк, считая комментарии и пустые строки.
- TypeScript проверяет типы JavaScript без сборки: `allowJs`, `checkJs`, `strict`, `noEmit`.
- Поиск повторов: не больше 2% в коде и 10% в тестах.
- Покрытие: текстовый отчёт, HTML и LCOV, включая неисполненные файлы.
  Процент покрытия пока информационный, без произвольного обязательного порога.

Отчёты доступны в GitHub Actions как `quality-reports`. Эти проверки выполняются
также после вливания в `main`. Новый коммит отменяет устаревший прогон того же PR.
Зависимости закреплены в `tools/package-lock.json`, установка в Actions выполняется через `npm ci`.

Пока рабочего кода продукта нет, вывод явно сообщает об этом. Тесты инфраструктуры
не считаются тестами продукта: появление рабочего кода без тестов продукта вызывает ошибку.
Само наличие теста не доказывает полноту проверок — ожидаемый результат сверяют с требованиями.

## Мутационные тесты — только вручную

После вливания workflow в `main`: **Actions → mutation → Run workflow**, затем
выберите нужную ветку. Автоматического запуска на PR, push или по расписанию нет.
Агент не запускает эту проверку без явного запроса пользователя.

Используется тот же `unclebob/mutator`, что в sdd-planner, с закреплёнными коммитами
mutator и crapper. Проверяется весь рабочий JavaScript-код, включая места без покрытия.
`tools/`, тесты и `*.config.mjs` в мутационный прогон продукта не входят.
Выжившая мутация или ошибка исходных тестов делает запуск неуспешным.
Мутации проверяются только тестами продукта, в рабочей папке mutator, где изменённый файл — копия,
а остальное — ссылки на исходное дерево. Поэтому тесты продукта ищут сервер от текущей папки
(корень репозитория), а не от места файла теста и не через git: иначе запустится неизменённый код.
Отчёты сохраняются как `mutation-reports`. Ограничение времени — 120 минут.
Без рабочего кода запуск явно сообщает, что мутационная проверка не выполнялась.

## Границы проверки

Проверка сложности выполняется ESLint, повторов — jscpd. Отдельные crapper/CRAP,
dryer и проверка графа зависимостей из прежнего проекта сейчас не перенесены.
Старые эталоны, допуски накопленных ошибок и тесты sdd-planner не используются.

Зелёные Actions сами по себе не запрещают вливание красного PR: для этого владелец
включает обязательные проверки ветки в настройках GitHub.
