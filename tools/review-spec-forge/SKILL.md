# Проверка простоты Spec Forge

Скилл для разработчиков самого расширения. Проверку начинают в новом окне Claude или ChatGPT. Проверяемый продукт предназначен для GigaCode CLI; его ограничения и целевые модели бери из требований репозитория.

## Вход и границы

1. **PR:** получи описание, исходную и проверяемую версии, полный список изменённых файлов и разницу между ними. Используй основание PR, которое может отличаться от `main`. Зафиксируй SHA проверяемого коммита. Проверяй только проблемы, добавленные или усиленные этим PR.
2. **Без PR:** проверь переданный код, указанные файлы или выбранную разницу версий. Если область неясна, уточни её одним вопросом. Для целого файла без сравнения оцени текущее содержимое; не приписывай проблемы последнему изменению без основания. Наличие PR и GitHub для этого режима не требуется.
3. Прочитай применимые `AGENTS.md`, требования и правила разработки, включая правила тестовых случаев, если они затронуты. Остальной репозиторий читай только для проверки соответствия этим правилам и требованиям. Не превращай проверку в обследование проекта и не добавляй замечания к постороннему коду.
4. Недоступный файл, неполная разница или отсутствующее основание проверки — ограничение, а не подтверждение отсутствия проблем. Укажи, что удалось проверить. Если подтверждение замечания требует кода за пределами области, не расширяй её самостоятельно и обозначь недостающие сведения.

## Факты и оценка

| Кто | Работа |
|---|---|
| Существующие инструменты GitHub или локальный Git | Версии, состав и объём изменений; доступные результаты CI для проверяемой версии |
| Проверяющий агент | Сопоставление с требованиями, оценка необходимости усложнений, сводка тестовых случаев и выводы |
| Владелец | Решение, какие замечания требуют исправлений |

Используй уже имеющиеся средства, без собственного сборщика и новых проверок CI. Отдельно покажи код, инструкции и данные тестов: большое число файлов само по себе не доказывает проблему. Отсутствие CI не мешает анализу. Учитывай назначение PR: падающие тесты новых критериев могут ожидать реализации. Результат другой версии не выдавай за проверку текущей.

## Направления проверки

Проверь применимые направления; для остальных достаточно отметить, что они не затронуты.

| Направление | Что выяснить |
|---|---|
| Код | Какие новые механизмы, уровни вызовов или повторные реализации появились? Какую текущую потребность они обслуживают? Возможен ли более прямой вариант с тем же поведением, включая ошибки и существенные ограничения? |
| Инструкции | Не повторяют ли правила друг друга, подсказки или проверки инструмента? Понятно ли, где принимается каждое решение? Не перекладывается ли механическая работа на модель? Оцени изменение всего читаемого на затронутом пути контекста, включая справки и ответы инструмента; перемещение текста между файлами само по себе не означает сокращения. |
| Пользовательский путь | Какие обязательные действия, вопросы, подтверждения и документы добавились? Для каждого подозрительного шага укажи его место, назначение и последствие. Проверь затронутые переходы и продолжение после перерыва: понятен ли следующий шаг, не требуется ли заново сообщать известные сведения или повторять работу? |
| Тестовые случаи | Составь сводку по проверяемому поведению и требованиям. Чем отличаются похожие случаи? Не повторяют ли они одну проверку без нового условия или результата? Учитывай правила проекта: похожие данные и независимые примеры не являются лишними сами по себе. Предложение упростить тесты должно сохранять проверяемое поведение. |

Полное ревью ошибок кода, безопасности и производительности в эту проверку не входит. Применяй критерии к цели Spec Forge, а не как повод расширить требования продукта.

Если доступны сабагенты и есть независимая работа, можно поручить им отдельные направления. Передай каждому одинаковую проверяемую версию, границы, применимые правила и запрет изменений. Сам проверь основания полученных замечаний, убери повторы и разреши противоречия перед итогом. Без сабагентов выполни те же проверки последовательно.

## Основания замечания

Для каждого замечания покажи:

- конкретные места в проверяемом материале; для повтора — оба места, действительно прочитанные в разрешённых границах;
- проблему и её последствие для пользователя, модели или сопровождения;
- основание в требованиях или конкретную техническую причину считать решение избыточным;
- более простой вариант и условия сохранения нужного поведения;
- что подтверждено источниками, а что остаётся предположением или требует проверки.

Перед выводом проверь разумное объяснение текущего решения: требования совместимости, порядок действий, обработку ошибок, независимость случаев. Внутренний механизм не обязан прямо называться в FR. Повтор между требованием, инструкцией и тестом может быть оправдан их разными назначениями. Сравни пользу упрощения с ценой переделки и вариантом оставить всё как есть. Не назначай произвольные пределы файлов, строк или число обязательных замечаний. Отсутствие обоснованных замечаний — допустимый результат.

## Отчёт

Верни один отчёт в диалоге:

1. **Область и версия:** что проверено и кратко что меняется. Для PR — ссылка и SHA; без PR — файлы или обозначение переданного материала.
2. **Замечания:** сначала наиболее существенные, с основаниями выше. Непроверенные предположения отделяй от подтверждённых фактов. Для мест в PR используй ссылки на проверенную версию; для локальных файлов — путь и строку.
3. **Сводка тестов:** если тесты затронуты, таблица «Поведение / Требование или правило / Случаи и их различия» со ссылками. Объединяй строки по смыслу, не перечисляй каждый служебный файл случая. Отсутствующую связь с требованием не выдумывай.
4. **Ограничения:** недоступные материалы, непроверенные выводы и результаты запусков, которых нет. Чтение инструкций и зелёный CI не доказывают работу целевых моделей в GigaCode CLI.

После отчёта решение принимает владелец. Не исправляй файлы, не публикуй комментарии в GitHub и не запускай мутационные тесты без его явного запроса. Разделение PR не предлагай и не выполняй, пока владелец сам об этом не попросит.
