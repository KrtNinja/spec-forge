## Что не должно измениться (качество)

- Мутируется весь рабочий JavaScript-код: тот же список файлов `product` из `tools/check.mjs`, с `--no-coverage --mutate-all`.
- Мутация убита, если тесты продукта упали или вышли за предел времени; выжившая мутация или упавшие исходные тесты делают запуск красным.
- Закреплённые коммиты mutator и crapper не меняются.

Доказательство для PR: число мест мутаций и число убитых по каждому файлу до и после совпадают (отчёты `.metrics/mutate/`, артефакт `mutation-reports`).

## Почему сейчас долго

Время ≈ число мутаций × время всех тестов продукта ÷ 2.

- `tools/check.mjs`, `mutate()`: на каждую мутацию запускаются все тесты продукта (`node --test` со всеми файлами), `--max-workers 2`.
- Тестов 157; каждый случай `tests/mcp/` запускает свой процесс сервера (`exchange` в `tests/server.mjs`). Замер вне Actions: около 12 с на 2 ядрах, Node.js 22.23.4 (не целевая версия — ориентир, а не точная цифра).
- Растут и код (мутации), и случаи (время набора), поэтому рост быстрее линейного.
- `node --test` не останавливается на первом упавшем тесте: убитая мутация всё равно проходит весь набор. В зелёном прогоне убиты все мутации.
- Если мутация подвешивает сервер, каждый случай ждёт свои 2 с (`timeout` в `tests/server.mjs`), и мутация висит до предела mutator.
- mutator берёт файлы по одному; одновременно идут только мутации одного файла.

Число мутаций не измерено: просмотр мест (`--scan`) требует установленного crapper с tree-sitter.

Что известно о mutator на закреплённом коммите (README и `src/mutator/cli.py`):
- путь к файлу в аргументах ограничивает прогон этим файлом;
- исходные тесты запускаются один раз в настоящем дереве до мутаций; предел времени мутации — 10 × длительность исходных тестов, не меньше 2 с (`--timeout-factor`);
- `--max-workers` по умолчанию — по одному на ядро; берётся меньшее из предела, числа ядер и числа мест;
- рабочие папки — `target/mutation-workers`, отчёты — `.metrics/mutate/<пространство имён>.edn`;
- `--verbose` печатает каждую команду тестов и каждую мутацию;
- коды завершения: 0 — все убиты, 2 — упали исходные тесты, 3 — есть выжившая.

## Шаг 1. Замер

До изменений получить по одному полному прогону: по каждому файлу — число мест, время, сколько мутаций вышло за предел времени; общее время. Цифры выводить так, чтобы владелец видел их в итогах запуска Actions без чтения журнала. Эти же цифры после шагов 2–4 показывают выигрыш и подтверждают, что состав не изменился.

Замер нужен, чтобы понять, какой шаг даёт основной выигрыш. Если он покажет другую главную причину, чем описано выше, — сообщи владельцу до продолжения.

## Шаг 2. Отдельное задание Actions на каждый файл

Список файлов — тот же, что `product` в `tools/check.mjs`, без второго источника правды. Задания идут одновременно; время по часам становится равным самому долгому файлу, а не сумме.

Критерии:
- итог запуска красный, если красное хотя бы одно задание;
- падение одного задания не отменяет остальные: владелец видит все выжившие мутации за один запуск;
- отчёты всех заданий доступны владельцу как сейчас (`mutation-reports`), без затирания друг друга;
- новый файл в `server/` попадает в прогон без правки `mutation.yml`.

## Шаг 3. Число одновременных мутаций — по ядрам

Сейчас жёстко `--max-workers 2`. Выясни, зачем выбраны 2 и `NODE_OPTIONS: --max-old-space-size=1024` (история файла, PR). Если причина — память, проверь её замером. Число бери из окружения, а не константой. Не проверено: у GitHub для открытых репозиториев 4 ядра.

Учти, что каждый случай запускает отдельный процесс Node.js: при нехватке ядер или памяти случаи начнут выходить за 2 с, и мутации будут «убиты» ложно. Проверка: число убитых и выживших совпадает с замером шага 1, а исходные тесты устойчиво проходят.

## Шаг 4. Остановка тестов на первом падении — только для мутаций

Мутация убита первым упавшим тестом; остальные тесты ничего не добавляют. Это же убирает долгое ожидание при подвешенном сервере.

Критерии:
- обычные `npm --prefix tools test` и `coverage` не меняются и по-прежнему показывают все падения;
- исходные тесты перед мутациями проходят полностью;
- после остановки не остаётся работающих процессов сервера и тестов;
- работает на Node.js 22.5.1.

Не проверено: в Node.js 22.5.1, по-видимому, нет готового ключа остановки на первом падении. Возможные направления — свой обработчик отчёта тестов, завершающий запуск на первом падении, или небольшая обёртка в `tools/`. Выбор и проверка — за тобой.

## Не входит в эту работу

Решения владельца, 13 ноября 2026:

- **Следующей итерацией** — режим «перед вливанием»: мутировать только файлы `server/`, изменённые относительно общего предка с `main`; полный прогон остаётся перед релизом. Заметки к нему:
  - список файлов брать из `git diff` с общим предком, а не через `--changed` mutator: тот смотрит `git status`, а в Actions рабочее дерево чистое;
  - встроенный разностный режим mutator (перезапуск выживших и функций с изменённым текстом) не использовать: ему нужен снимок `.metrics/mutate` между запусками, а это состояние, которое может незаметно устареть;
  - известный пробел: ветка ослабила или удалила существующий случай, а файл сервера не менялся — его мутации не перепроверяются. Отдельным правилом не закрывается: это ловит полный прогон перед релизом.
- **Отложено** — запускать для мутации только тесты, которые исполняют мутируемый файл (по покрытию каждого случая). Качество не теряется: тест, не исполнивший строку, убить мутацию не может. Но это самый большой объём служебного кода; возвращаться, только если после шагов 2–4 прогон всё ещё долгий.
