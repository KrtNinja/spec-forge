# Подготовить Spec Forge к самостоятельному использованию

Репозиторий: `KrtNinja/spec-forge`.
Ветка задания: `criteria/release-readiness`.
Основание ревью: `82492695913b54e6e4608a053fc8b41b7ad3f996` (main, 12 ноября 2026).
Цель — устранить четыре замечания и подтвердить работу расширения в GigaCode CLI.

## Поручение следующему агенту

Подготовь **PR критериев** по заданию ниже в этой ветке. Найди открытый PR с head `criteria/release-readiness` и base `main`, продолжай его. Пока ветка содержит только это задание: зелёный CI ещё не означает готовность критериев или продукта.

Сначала прочитай:
- `AGENTS.md`;
- `docs/product-requirements.md` и `docs/core/design.md`;
- требования и устройство `sf-grill`, `sf-spec`, `sf-review`, `sf-note` в `docs/`;
- `tools/README.md`;
- затронутые случаи в `tests/mcp/`, `tests/protocol.test.mjs`, `tests/server.mjs`.

Сверь замечания с текущей версией ветки. Выполненное повторно не переделывай. Согласованные продуктовые решения сохраняй; конкретное противоречие обсуждай с владельцем.

В этом поручении: тестовые случаи, необходимые тексты ответов и уточнения договора, README и связанные документы. Код реализации в `server/`, кроме `contract.mjs` и `texts.mjs`, пока не менять. Точные пользовательские тексты представить владельцу в PR критериев.

После подготовки критериев покажи владельцу, какие новые тесты воспроизводят ошибки и ожидаемо падают, какие проверки проходят и что проверяется только в GigaCode CLI. PR оставить Draft, самостоятельно не вливать. Реализацию начинать по отдельному поручению владельца: отдельная ветка и PR в `criteria/release-readiness`, как требует `AGENTS.md`.

## 1. Находить задачу после утраты одобрения

Проблема: при автоматическом подборе `sf-spec` и `sf-review` задача исключается по наличию строки одобрения, хотя её сумма уже не совпадает с содержимым. С явно указанным именем та же задача правильно определяется как требующая повторного одобрения.

Основания: FR-23, FR-24; `docs/core/design.md`, разделы «Состояние и переходы» и «Вход в работу и выбор задачи».
Места ревью: `server/status.mjs:48,74,163`, `server/spec.mjs:45–46`.

Воспроизведение:
1. Использовать документы `tests/mcp/status/approved-changed/before/`.
2. Вызвать `status` с `command: "sf-spec"` без `task`: сейчас ответ «Задач без одобренных требований нет».
3. Повторить для `sf-review` с `touched: false, agent: false`: задача тоже не найдена.
4. С `task: "order-search"` обе команды сообщают, что одобрение не действует.

Критерии:
- Для обеих команд без имени единственная подходящая задача с несовпадающей суммой находится; ответ называет необходимость повторного одобрения.
- Если подходящих задач несколько, изменённая задача участвует в выборе.
- Действительно завершённая задача с действующим одобрением по-прежнему исключается.
- Явно указанная задача сохраняет прежнее корректное поведение.
- Состояния с открытыми вопросами и блокирующими замечаниями сверить с действующей таблицей переходов; новые правила для них самостоятельно не вводить.

Использовать текущие документы и проверки состояния. Нового файла состояния не требуется.

## 2. Сохранять сервер работоспособным при ошибке записи ссылок

Проблема: `link` пишет документы по очереди; ошибка записи выходит необработанной и завершает MCP-сервер. Предыдущие документы к этому моменту могут быть изменены.

Основания: обработка неудачного вызова по FR-28; конкретная ошибка ввода-вывода при работе `link`.
Места ревью: `server/link.mjs:35–37`, `server/mcp.mjs:80–83`.

Воспроизведение на Linux от обычного пользователя:
1. Скопировать `tests/mcp/link/numbers/before/` во временную папку.
2. Оставить чтение `docs/order-search/spec.md`, запретить запись в него.
3. Запустить MCP-сервер с этой папкой как рабочей.
4. Вызвать `link`, затем `ping` в том же процессе.
5. Сейчас: `EACCES`, код завершения 1, ответа вызова и ответа `ping` нет; `brainstorming.md` уже изменён.

Критерии:
- Ожидаемая ошибка записи возвращается как неудачный вызов с `isError: true` и понятным текстом с именем файла.
- Тот же процесс обрабатывает следующий запрос.
- Если до ошибки были успешно изменены документы, ответ сообщает какие; полного успеха не заявляет.
- После устранения причины повторный вызов завершает работу корректно; уже исправленные ссылки не повреждаются.
- Успешные вызовы, переводы строк и обработка ошибок чтения сохраняют прежнее поведение.

В PR критериев согласовать точный текст ошибки и минимально уточнить договор обработки записи в `docs/core/design.md` и текстах ответа. Подтвердить ошибку реальным отрицательным исходом записи: существующий случай ошибки чтения недостаточен. Использовать текущий тестовый запуск, без отдельной системы тестирования. Полная атомарность записи нескольких документов не входит в задание.

## 3. Уточнить подсказку перехода к требованиям

Проблема: `server/texts.mjs:108` говорит «Когда вопросов не останется», хотя FR-10 допускает подготовку требований с неблокирующими открытыми вопросами. `tests/mcp/status/ready-for-spec/` содержит именно такой вопрос и закрепляет эту фразу в ожидаемом ответе.

Скилл `sf-grill` точнее: обсуждение заканчивается, когда не осталось вопросов, которые можно задать сейчас. Подсказка инструмента не должна вводить другое условие.

Критерии:
- Подсказка не требует закрыть неблокирующие вопросы перед подготовкой `spec.md`.
- Готовность содержания обсуждения по-прежнему оценивает агент; отсутствие блокирующих вопросов само по себе не означает, что обсуждение завершено.
- Блокирующий вопрос сохраняет запрет перехода.
- Одобрение по-прежнему требует решения всех открытых вопросов по FR-21.
- Изменены только связанные тексты и ожидаемые ответы; логика вопросов и процесса не расширяется.

Предлагаемый текст для проверки владельцем: «Когда обсуждение завершено — предложить подготовить требования. Неблокирующие вопросы могут оставаться открытыми».

## 4. Дать новичку начало работы в README

Проблема: README описывает продукт и отправляет в требования для разработчиков. Подключение спрятано в `docs/core/design.md:23`.

Добавить короткий путь:
1. Какие версии GigaCode CLI и Node.js проверены.
2. Как получить и подключить расширение.
3. Как открыть GigaCode в проекте, для которого готовятся требования.
4. Как начать с `/sf-grill` и описания идеи.
5. Для чего нужны `sf-grill`, `sf-spec`, `sf-review`, `sf-note`.
6. Где появятся документы и что означает завершение работы.

Команды установки сверить с актуальной документацией GigaCode CLI, затем проверить при реальном запуске. Пользователю расширения не нужна установка зависимостей разработки из `tools/`. Версию Node.js 22.5.1, проверенную CI, не выдавать за доказанный минимальный порог совместимости. Непроверенные версии и платформы не объявлять поддерживаемыми.

Критерий — коллега по README подключает расширение и начинает задачу без устных пояснений владельца. Отдельное большое руководство не требуется.

## Проверка в GigaCode CLI после исправлений

Целевые модели: Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash.

На каждой модели пройти одну небольшую задачу и проверить:
- расширение, четыре скилла, `spec_forge` и общие правила действительно загружаются;
- идея доходит до полезного `spec.md`, предложения агента не становятся решениями без пользователя;
- простая задача не превращается в обязательную длинную анкету;
- после перерыва задача продолжается по сохранённым документам;
- с неблокирующим вопросом можно подготовить требования, но нельзя одобрить;
- `sf-review` выполняется в отдельном контексте, замечания разбираются с пользователем;
- одобрение выполняется только по явному решению пользователя;
- изменение одобренного документа замечается и требует повторного одобрения.

Кратко сохранить в `_work/release-readiness-results.md`: SHA, версию CLI, Node.js, модель, сценарии, фактический результат и обнаруженные проблемы. Если окружение или модель недоступны, явно отметить непроверенные сценарии и передать владельцу короткие шаги проверки. Не заменять реальный прогон имитацией ответов модели и не объявлять готовность по одному зелёному CI.
