# Spec Forge

Расширение для GigaCode CLI: скиллы, правила и проверки, которые помогают пройти путь от идеи в одну фразу до одобренных требований по подходу Spec-Driven Development — разработки на основе требований.

Главный результат — качественные требования, которые можно передать в разработку без повторного выяснения смысла. По этим документам разработчик или агент пишет код, не угадывая, как должна вести себя система. Прохождение этапов и заполнение шаблонов сами по себе не являются результатом.

Написание кода по подготовленным единицам работы — отдельная задача, которая не входит в Spec Forge.

Главные приоритеты — удобство пользователя и бережное отношение к контексту модели. Объём обсуждения и документов должен соответствовать задаче. Простая задача должна оставаться простой.

Пользователь описывает идею и принимает решения о поведении продукта. Агент самостоятельно исследует доступные источники, выявляет неизвестные и противоречия. Детерминированные инструменты берут на себя механические действия и проверки, чтобы модель могла сосредоточиться на содержании и смысле требований.

## Начало работы

Нужны Git, Node.js и GigaCode CLI.

Целевые модели: Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash.

Скачайте расширение в отдельную папку и подключите её. Замените путь на абсолютный путь к скачанной папке:

```sh
gigacode extensions link "/путь/к/spec-forge"
```

Папку расширения сохраняйте на этом месте. Устанавливать зависимости из `tools/` не требуется.

Перейдите в проект, для которого готовите требования, и запустите GigaCode:

```sh
cd "/путь/к/вашему-проекту"
gigacode
```

Если GigaCode уже был открыт, перезапустите его. Внутри сессии `/extensions` показывает подключённое расширение, `/skills` — четыре скилла `spec-forge:sf-…`, `/mcp` — сервер `spec-forge` и инструмент `spec_forge`. Если они не появились, проверьте путь подключения и сообщения CLI.

Начните с идеи, например:

```text
/spec-forge:sf-grill Покупатель должен находить свой заказ по номеру
```

Агент уточнит источники и имя папки задачи, обсудит требования и предложит следующий шаг. Отвечайте на вопросы и принимайте решения; предложения агента становятся требованиями после вашего согласия.

| Команда | Для чего нужна |
|---|---|
| `/spec-forge:sf-grill` | Начать или продолжить обсуждение идеи |
| `/spec-forge:sf-spec` | Подготовить требования по принятым решениям |
| `/spec-forge:sf-review` | По желанию проверить требования в отдельном контексте и разобрать замечания |
| `/spec-forge:sf-note` | Добавить сведения, ответить на отложенный вопрос или попросить правку |

После перерыва вызовите нужную команду с именем задачи, например `/spec-forge:sf-spec order-search`. Без имени расширение найдёт подходящую задачу или предложит выбрать из нескольких.

Документы появятся в `docs/<имя-задачи>/` вашего проекта: обсуждение — `brainstorming.md`, требования — `spec.md`, открытые вопросы и ответы — `questions.md`, материалы изучения и проверки — в `_work/`. Неблокирующие вопросы допускают подготовку требований; перед одобрением нужно решить все открытые вопросы и блокирующие замечания, пройти автоматические проверки.

Вы одобряете документ явно. Завершение — сообщение **«Документ с требованиями одобрен»** со ссылкой на `spec.md`. После изменения одобренного документа потребуется повторное одобрение. Написание кода по требованиям — следующая самостоятельная задача.

## Для разработчиков расширения

[Продуктовые требования](docs/product-requirements.md) описывают согласованный путь от идеи до одобренного документа с функциональными требованиями: основа со ссылками на требования этапов. Это документ для разработки самого Spec Forge, а не инструкция для агента, использующего расширение. Изменения процесса согласуются и фиксируются в нём через PR.
