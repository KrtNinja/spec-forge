# Правила разработки Spec Forge

Обязательны для агентов, изменяющих этот репозиторий. Это правила разработки, а не дополнительная инструкция для агента, который составляет требования.

## Цель

Помочь пользователю получить качественный документ требований на flash-моделях в GigaCode CLI: Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash. Простая задача должна оставаться простой.

## При каждом изменении

1. **Понятный язык.** Проверь добавленные и изменённые файлы на англицизмы, кальку и технический жаргон. Текст для пользователя должен быть понятен без расшифровки. Точные имена команд, файлов и моделей сохраняй.
2. **Бережный расход контекста.** Правила скиллов и инструкции должны помогать агенту выполнить текущую задачу. Не дублируй проверки, подсказки и переходы, которые уже обеспечивает детерминированный инструмент. Перед добавлением правила проверь, зачем оно нужно модели и нельзя ли обойтись без него. Разнос текста по файлам сам по себе не уменьшает объём чтения; оценивай весь загружаемый контекст.
3. **Развилки обсуждать.** Если требование непонятно или в ходе размышлений возникает выбор поведения, этапов либо устройства инструмента — уточни у разработчика до принятия решения. Не выдумывай требования и не добавляй сложность ради предполагаемых будущих нужд.
4. **Рутина — инструменту.** Детерминированный инструмент помогает агенту ориентироваться, продолжать работу и переключаться между скиллами; выполняет механические действия и проверки. ИИ отвечает за содержание и смысл. Не заставляй модель помнить и повторять работу инструмента.
5. **Изменения через PR.** Все изменения в репозитории вноси через pull request (PR), если пользователь явно не попросил иначе.
6. **Тесты проверяют поведение.** Для новой или изменённой логики JavaScript проверяй конкретный результат по требованиям, включая значимые граничные случаи и ошибки. При исправлении ошибки добавь тест, который воспроизводит её и падает до исправления. Не ослабляй проверки ради успешного прогона.
7. **Мутационные тесты — вручную.** Не запускай их автоматически в PR или без явного запроса пользователя. Пользователь запускает их самостоятельно через GitHub Actions.
8. **Сначала процесс, затем реализация.** До согласования пользовательского процесса не проектируй команды, статусы, скиллы и форматы хранения. Основывай решения на согласованном описании процесса. Существующий код не является основанием для сохранения поведения или сложности. Прежний проект [sdd-planner](https://github.com/KrtNinja/sdd-planner) — источник отдельных наработок, а не основа: наличие правила в нём не является согласованием для Spec Forge. Не переноси автоматически обязательный обход всех тем, прежнюю глубину детализации, дополнительные подтверждения, внутренние команды, состояния, способы хранения и последующие этапы.
9. **Сложность требует основания.** Не добавляй обязательные этапы, вопросы, документы и подтверждения без конкретной пользовательской потребности. Списки тем и шаблоны не должны превращаться в обязательную анкету.
10. **Проверяй пользу изменения.** Для изменений процесса в PR кратко объясняй, что станет проще или надёжнее для пользователя и как изменятся действия пользователя и загружаемый контекст. Сокращение отдельного файла не доказывает упрощение всего пути.
11. **Разделяй доказательства.** Успешные тесты JavaScript подтверждают проверенное поведение кода. Работоспособность инструкций на целевых flash-моделях подтверждается отдельной проверкой в GigaCode CLI. Не заявляй её без такого прогона.

## Текущий этап

Сейчас репозиторий используется для согласования процессов Spec Forge. Реализацию функций начинай только по отдельному поручению владельца. Согласование описания процесса само по себе не разрешает его реализацию.

## Источник продуктовых требований

Требования устроены от общего к частному. Перед проектированием или изменением поведения расширения прочитай основу — [docs/product-requirements.md](docs/product-requirements.md) — и требования затронутого этапа в его папке, например `docs/sf-spec/`. Общее устройство описано в [docs/core/design.md](docs/core/design.md), устройство этапа — в `design.md` его папки.

Правила изменения документов:
- изменения процесса сначала согласуй с владельцем и вноси через PR: сначала в требования, затем в устройство;
- в `requirements.md` этапа: строка «Зависит от», таблица распределения работы на этапе, FR этапа и сценарии «Когда — Тогда», а после реализации — ссылка на тесты; в `design.md` этапа — только его устройство;
- ссылайся на чужие FR только по номеру, не пересказывая их; номера FR сквозные и не меняются;
- строка «Зависит от» в требованиях этапа перечисляет все FR, на которые он опирается; при изменении FR перечитай этапы, которые от него зависят;
- ориентир — около 10 000 знаков (букв и цифр) на файл; превышение — повод разделить файл, а не ошибка;
- нерешённые вопросы документов не трактуй как разрешение самостоятельно выбрать поведение.

Эти файлы предназначены только для разработки расширения: не включай их в постоянный контекст агента, который составляет пользовательские требования.
