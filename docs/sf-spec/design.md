# sf-spec: устройство

Как выполнены [требования этапа](requirements.md). Опирается на [общее устройство](../core/design.md).

Документы, которые скилл читает после `status`: `brainstorming.md`, `questions.md`, `spec.md`, если он есть.

## Вход

`status` с командой `sf-spec`:
- без задачи — подходящие задачи по общему устройству: нет — начать новую через `/sf-grill`, одна — продолжить её, несколько — выбрать;
- задачи с названным именем нет — `sf-spec` новую задачу не начинает и отправляет к `/sf-grill`;
- `spec.md` нет, а источники не изучены или вопросы блокируют — обсуждение не закончено: `/sf-grill <имя>` и строка Tip. Иначе — подготовить `spec.md`.

С `spec.md` строки переходов общего устройства, сверху вниз:
- `check` находит ошибки в любом документе задачи — исправить;
- черновик, открыты вопросы — разобрать их; одобрить нельзя (FR-21);
- черновик, вопросов нет — «Проверить требования» (`/sf-review <имя>`, рекомендуется) или «Одобрить» (FR-16). Как запускается проверка, описано в [sf-review/design.md](../sf-review/design.md);
- одобрено, сумма совпадает, вопросов нет — работа завершена, новые сведения — через `sf-note`.

## Подготовка требований

- Одно правило — одна запись `FR-…`: правило текстом, «Пример» одной строкой, «Основание» — номера решений. Несколько исходов в примере — через «;».
- Образец `spec.md` с образцом FR — только в `sf-spec`.
- Требования без кода: ни путей и файлов, ни классов и методов. Это правило в тексте `sf-spec`, а не проверка: проверка не отличит ссылку на код от имени файла, которое описывает поведение, например выгрузку `orders.csv`. В `brainstorming.md` и `_work/` ссылки на код допустимы.
- Остаётся модели: FR-14, FR-15.

## Проверка и одобрение

- После правки — `link` и `check` по общим правилам. Открытые вопросы `check` называет сам.
- `check` выдал строку одобрения — агент вызывает `status` и предлагает его варианты. Строку одобрения вставляет только по явному решению пользователя, без изменений, и снова вызывает `check` — тот выдаёт сообщение FR-22.
