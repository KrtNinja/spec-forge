# План реализации Spec Forge

Временный документ: порядок реализации, отложенные решения и подсказки к блокам. Устройство системы описано в [design.md](design.md) и `design.md` этапов как готовое. Постоянные документы на этот файл не ссылаются; после блока 8 он удаляется.

## Как продолжить работу

Поручение агенту — «Продолжи работу по docs/core/steps.md». Каждый блок делается двумя PR — критерии и реализация, по разделу «Критерии и реализация» [AGENTS.md](../../AGENTS.md). Ветка критериев блока — `criteria/block-N`.

1. Текущий блок — тот, у которого открыт PR из `criteria/block-N` в main. Дальше работай по AGENTS.md этой ветки: состав работы — в описании PR критериев, что осталось — падающие тесты.
2. Открытого PR критериев нет — составь критерии следующего блока вместе с владельцем: начни с решений, записанных у блока, развилки обсуждай вопросами.

## Блоки

1. Манифест, MCP-сервер с пустыми `status`, `check` и `link`, правила без образцов записей, тесты обмена с MCP-сервером.
2. `status`: выбор задачи, проверка имени папки, этап и следующий шаг, проверка источников, задание на изучение. `check` для `_work/context.md`.
   - Для команд, кроме `sf-grill`, и для задачи со `spec.md` `status` пока отвечает «не реализовано»; эти строки переходов — в блоках 3–6.
3. `check` для `brainstorming.md` и `questions.md`: формат, номера, блокирующие вопросы, следующие свободные номера. Образцы `D-…` и `Q-…` в правилах. Скилл `sf-grill` с `grilling`.
4. `check` для `spec.md`: пример и основание FR, заменённые основания, ссылки, размер, строка статуса и приведение текста перед подсчётом суммы, условия одобрения. `link`. Скилл `sf-spec`.
5. `check` для `review.md`, `link` для `R-…`, путь проверки в `status`. Скилл `sf-review`.
6. `status` для `sf-note` и строки одобренной задачи, изменение одобренного `spec.md` — повторное одобрение, зависящие FR в `check`, предложение закоммитить после одобрения. Скилл `sf-note`.
7. Прогон проверочных ситуаций и правки по его итогам.
   - Прогон 2026-11-12: Haiku в эмуляции GigaCode с настоящим `server/mcp.mjs`, путь от идеи до одобрения, `sf-note` после одобрения, повторная проверка в чистой сессии, ветки без отдельного агента. Ошибки записи ловили `check` и `status` — пишущие действия сверх `link` не нужны. Ответы на английский не уходили; проверяющий агент `status` не вызывал; `sf-note` без смены смысла `spec.md` не трогал.
   - Правки, решённые с владельцем:
     1. `/sf-review` в чистой сессии после разобранной проверки — агент переспрашивает: `status` предлагает «Повторить проверку» или «Одобрить», хотя команду для этой сессии дал он сам. Решение: для `sf-review` при `touched` — нет и без замечаний без решения в последнем разделе `status` сразу называет путь «здесь», как до первой проверки; при `touched` — да — как сейчас. Ответ — как до первой проверки: «готовы к проверке», затем что мешает одобрению и путь; препятствия называются и до первой проверки.
     2. Агент пересказал задание на изучение и выбросил «Каждый источник запиши так, как он записан выше»; агент изучения записал файлы вместо папки, и `status` назвал папку недоступной. Решение: `sf-grill` передаёт задание из ответа `status` как есть и дописывает, что выяснить. Текст задания в `texts.mjs` не меняется.
     3. `touched` и `agent` неверны в 3 из 6 вызовов. Решение: уточнить их строки в `sf-review` — готовил или правил `spec.md` до запуска `sf-review` тоже считается; `agent` — есть ли инструмент запуска отдельного агента. Те же уточнения — в описаниях полей договора и в ошибке без признаков; в стенде `run-check.md` договорённость о поручении названа инструментом запуска.
     4. `sf-note` заводит вопрос `Q-…` ради записи подтверждения и ставит вопросу «Заменено». Решение: строка в правилах — сведения без открытого вопроса записываются решением с вопросом текстом; `check` — поле вопроса не из образца считается ошибкой. Полем считается пункт «- Имя: …» после первого поля образца; пункты до него — текст вопроса.
   - Проверка после реализации — повторный прогон по [run-check.md](run-check.md); он удаляется после блока 7.
8. Инструмент прогона на настоящем GigaCode: владелец запускает его сам, когда меняет правила, скиллы или ответы инструмента.
   - Решено с владельцем:
     - Инструмент запускается на компьютере с GigaCode, где нет Claude и Codex. Отчёт владелец отправляет Claude или ChatGPT, и вердикт выносит тот. Проверок сверх `check` и `status` в инструменте нет.
     - Используется только GigaCode, без запасного пути на другой модели.
     - Журнал вызовов `spec_forge` пишет MCP-сервер: аргументы и ответ каждого вызова, только когда задан путь к файлу журнала в переменной окружения; иначе сервер ничего не пишет. Это новая пишущая обязанность: правка «Что можно писать» в `core/design.md`, затем критерии и реализация.
   - Подсказки к критериям:
     - Пользователя играет сценарий. Реплики пишутся по смыслу, без номеров вопросов. Следующая реплика отправляется по условию на журнал или файлы задачи, например «`status` показал переход» или «появился `spec.md`». Общая реплика «продолжай» повторяется, пока условие не выполнено, но не больше заданного числа раз.
     - Ход — `gigacode -p` для новой сессии или `gigacode --resume <id> -p`, с `--approval-mode auto-edit --output-format json -m <модель>` и бюджетом ходов и времени. `session_id` берётся из вывода; `/clear` — новая сессия без `--resume`.
     - Стенд — копия образца проекта во временной папке с `.gigacode/settings.json`: в нём вызовы `spec_forge` разрешены в `permissions.allow`, запись истории не выключена.
     - Отчёт — один Markdown-файл: ожидания сценария и как выносить вердикт; по каждому прогону — модель, реплики и ответы агента, вызовы `spec_forge` между ними, коды возврата (53 — исчерпаны ходы, 55 — бюджет), итоговые документы задачи. Сценарий гоняется заданное число раз на каждой модели.
     - Место — `tools/model-run/`: скрипт, сценарии, образец проекта, порядок запуска. Это инструмент разработки, а не поведение расширения, поэтому он делается одним PR после вливания журнала.
     - Узнать первым прогоном: срабатывают ли `/sf-…` внутри `-p`; доходит ли переменная окружения до MCP-сервера, а если нет — как включать журнал иначе; проходит ли запуск отдельного агента без подтверждения.
