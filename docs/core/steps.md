# План реализации Spec Forge

Временный документ: порядок реализации, отложенные решения и подсказки к блокам. Устройство системы описано в [design.md](design.md) и `design.md` этапов как готовое. Постоянные документы на этот файл не ссылаются; после блока 7 он удаляется.

## Как продолжить работу

Поручение агенту — «Продолжи работу по docs/core/steps.md». Каждый блок делается двумя PR — критерии и реализация, по разделу «Критерии и реализация» [AGENTS.md](../../AGENTS.md). Ветка критериев блока — `criteria/block-N`.

1. Текущий блок — тот, у которого открыт PR из `criteria/block-N` в main. Дальше работай по AGENTS.md этой ветки: состав работы — в описании PR критериев, что осталось — падающие тесты.
2. Открытого PR критериев нет — составь критерии следующего блока вместе с владельцем: начни с решений, записанных у блока, развилки обсуждай вопросами.

## Блоки

1. Манифест, MCP-сервер с пустыми `status`, `check` и `link`, правила без образцов записей, тесты обмена с MCP-сервером.
2. `status`: выбор задачи, проверка имени папки, этап и следующий шаг, проверка источников, задание на изучение. `check` для `_work/context.md`.
   - Для команд, кроме `sf-grill`, и для задачи со `spec.md` `status` пока отвечает «не реализовано»; эти строки переходов — в блоках 3–6.
3. `check` для `brainstorming.md` и `questions.md`: формат, номера, блокирующие вопросы, следующие свободные номера. Образцы `D-…` и `Q-…` в правилах. Скилл `sf-grill` с `grilling`.
4. `check` для `spec.md`: пример и основание FR, заменённые основания, ссылки, размер, строка статуса и приведение текста перед подсчётом суммы, условия одобрения. `link`. Скилл `sf-spec`.
5. `check` для `review.md`, `link` для `R-…`, путь проверки в `status`. Скилл `sf-review`.
6. `status` для `sf-note` и строки одобренной задачи, изменение одобренного `spec.md` — повторное одобрение, зависящие FR в `check`, предложение закоммитить после одобрения. Скилл `sf-note`.
7. Прогон проверочных ситуаций и правки по его итогам.
   - Прогон 2026-11-12: Haiku в эмуляции GigaCode с настоящим `server/mcp.mjs`, путь от идеи до одобрения, `sf-note` после одобрения, повторная проверка в чистой сессии, ветки без отдельного агента. Ошибки записи ловили `check` и `status` — пишущие действия сверх `link` не нужны. Ответы на английский не уходили; проверяющий агент `status` не вызывал; `sf-note` без смены смысла `spec.md` не трогал.
   - Правки, решённые с владельцем:
     1. `/sf-review` в чистой сессии после разобранной проверки — агент переспрашивает: `status` предлагает «Повторить проверку» или «Одобрить», хотя команду для этой сессии дал он сам. Решение: для `sf-review` при `touched` — нет и без замечаний без решения в последнем разделе `status` сразу называет путь «здесь», как до первой проверки; при `touched` — да — как сейчас.
     2. Агент пересказал задание на изучение и выбросил «Каждый источник запиши так, как он записан выше»; агент изучения записал файлы вместо папки, и `status` назвал папку недоступной. Решение: `sf-grill` передаёт задание из ответа `status` как есть и дописывает, что выяснить.
     3. `touched` и `agent` неверны в 3 из 6 вызовов. Решение: уточнить их строки в `sf-review` — готовил или правил `spec.md` до запуска `sf-review` тоже считается; `agent` — есть ли инструмент запуска отдельного агента.
     4. `sf-note` заводит вопрос `Q-…` ради записи подтверждения и ставит вопросу «Заменено». Решение: строка в правилах — сведения без открытого вопроса записываются решением с вопросом текстом; `check` — поле вопроса не из образца считается ошибкой.
   - Проверка после реализации — повторный прогон по [run-check.md](run-check.md). Оба файла удаляются после блока 7.
