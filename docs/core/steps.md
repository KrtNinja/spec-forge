# План: единый прогон Spec Forge на моделях

Временный файл: удаляется, когда работы 1–3 влиты в main. Постоянные документы на него не ссылаются. Поручение агенту — «Продолжи работу по docs/core/steps.md». Код в этой ветке не меняется.

## Зачем

Сейчас владелец проверяет расширение так: скачивает репозиторий на рабочий компьютер, подключает к GigaCode CLI, выбирает модель, ведёт диалог на тестовых требованиях и пересказывает замеченное сильной модели. Прогон отнимает слишком много времени, а мелочи теряются при пересказе. Выгружать результаты с рабочего компьютера нельзя.

Решение владельца (17 ноября 2026): прогон ведёт сильная модель — Claude, ChatGPT или другая — и сама видит результат. Она играет пользователя, а требования составляет младшая модель её же семейства. Порядок прогона и вид результата одинаковы для любой ведущей модели, чтобы прогоны можно было сравнивать.

Этим решением прежнее «только GigaCode, без запасного пути на другой модели» уточняется: прогон на младшей модели — быстрая первая проверка при каждой правке правил, скиллов и ответов инструмента, а прогон в GigaCode остаётся редкой проверкой перед передачей пользователям.

Один прогон сам по себе мало что говорит. Владельцу нужны ответы на два вопроса, и каждый — сравнение двух прогонов одного сценария:

| Вопрос | Что с чем сравнивается |
|---|---|
| Мои правки стали мешать или помогли? | Расширение из main и расширение из ветки с правками |
| Подтверждается ли гипотеза, что инструмент помогает? | Чистый запрос без расширения и расширение из main или ветки |

## Что прогон доказывает

- Показывает: неясные и противоречивые инструкции, пропущенные шаги, лишние вопросы, плохо читаемый `spec.md`, ошибки инструмента.
- Не показывает: привычки Qwen3.8-flash-next, GLM-5.3-Flash и DeepSeek-V4.1-Flash и поведение самого GigaCode — приставку `/spec-forge:`, `AskUserQuestion`, загрузку правил по `paths`.

Поэтому по п. 11 [AGENTS.md](../../AGENTS.md) такой прогон не подтверждает работоспособность на целевых моделях. Эта оговорка стоит первой строкой каждого отчёта и сравнения.

## Роли

| Кто | Что делает |
|---|---|
| Ведущий — сильная модель | Готовит стенд, запускает исполнителя, отвечает ему за пользователя по роли из сценария, записывает диалог, пишет замечания. Ничего не чинит и исполнителю не подсказывает |
| Исполнитель — младшая модель того же семейства | Составляет требования: с расширением — как агент в GigaCode, без него — по чистому запросу |
| Судья — сильная модель в чистом контексте | Сравнивает пару прогонов, которых сам не проводил, и выносит вердикт по сценарию |
| Скрипт | Готовит стенд, вызывает `spec_forge` и пишет журнал, собирает отчёт, считает показатели пары и проверяет, что пара сравнима. Суждений не выносит |
| Владелец | Выбирает сценарий и пару, читает отчёты и вердикт, решает, что править |

## Устройство

Место — `tools/model-run/`: инструмент разработки, а не поведение расширения. `server/`, `rules/` и `skills/` не меняются.

### Варианты прогона

- **С расширением из `<ветка или коммит>`** — `main`, ветка с правками или любой коммит. Копия расширения берётся из этой версии через `git archive`, рабочая папка не меняется. Версия должна быть в локальном репозитории: перед прогоном её подтягивают `git fetch`.
- **Без расширения** — исполнитель получает только среду стенда и чистый запрос из `tools/model-run/bare.md`, общий для всех сценариев.

Сценарий и скрипты всегда берутся из текущей рабочей папки, поэтому обе стороны пары гоняются на одном и том же сценарии.

### Сценарий — `tools/model-run/scenarios/<имя>/`

Имя сценария — оно же имя папки задачи `docs/<имя>/`.

- `request.md` — тестовые требования: идея словами пользователя.
- `user.md` — для ведущего и судьи: роль пользователя (кто он, что знает о задаче, чего не знает, какие ответы даёт на ожидаемые вопросы) и раздел «На что смотреть» из двух частей. «Итог» относится к любому варианту, «Инструмент» — только к прогонам с расширением. Исполнитель этот файл не видит.
- `project/` — образец проекта, если идея ссылается на источники. Необязателен.

Данных с рабочего компьютера в сценариях нет.

### Скрипты

Два файла, каждый в пределе 350 строк. Обмен с сервером по MCP уже есть в `tests/server.mjs`. Не дублируй его: проверка повторов допускает не больше 2% в коде.

`tools/model-run/run.mjs` — прогон:

- `prepare <сценарий> <папка стенда> --leader <модель> --executor <модель> (--ref <ветка или коммит> | --bare)` — создаёт стенд вне репозитория: копия `project/`, копия расширения из `--ref` (`rules/`, `skills/`, `server/`, `gigacode-extension.json`) в подпапке, `start.md` и `meta.json`. В `meta.json` записываются ведущий, исполнитель, сценарий, сумма файлов сценария, вариант, версия и её коммит, дата. Папок `docs/`, `tests/`, `tools/` расширения и `user.md` в стенде нет: исполнитель не должен видеть документы разработчиков и роль пользователя.
- `call <папка стенда> '<аргументы JSON>'` — запускает `server/mcp.mjs` из копии расширения в стенде, делает один вызов `spec_forge` по MCP, печатает текст ответа и дописывает строку в `journal.jsonl`: время, аргументы, ответ, признак ошибки. Так исполнителю без MCP доступен настоящий инструмент, а журнал появляется без новой пишущей обязанности сервера. Без расширения `call` отвечает ошибкой.
- `collect <папка стенда>` — собирает один `report.md`: оговорка из раздела «Что прогон доказывает», `meta.json`, показатели прогона, диалог, вызовы `spec_forge` по порядку, ответы `check` и `status` по итоговым документам (только с расширением), сами документы задачи и пустой раздел «Замечания».

`tools/model-run/compare.mjs` — сравнение:

- `compare <стенд A> <стенд B> <папка сравнения>` — сравнивает ровно одну пару: по одному стенду на сторону. Сначала проверяет, что пара сравнима: совпадают ведущий, исполнитель, сценарий и сумма его файлов, различаются только вариант или версия. Несравнимая пара — ошибка с перечнем расхождений. Затем пишет `compare.md` и `key.json`. В `compare.md` стоят оговорка, показатели обеих сторон таблицей, диалоги и итоговые документы обеих сторон. Стороны названы «Первый» и «Второй» в случайном порядке, а какая из них какая — только в `key.json`.

Показатели прогона считаются из стенда, без суждений:
- дошёл ли прогон до конца или остановлен ведущим, и где;
- последний этап: последний ответ `status` в журнале; без расширения — есть ли `spec.md`;
- реплик пользователя, из них ответов вне роли;
- блоков `AskUserQuestion` в ответах исполнителя;
- вызовов `spec_forge`, из них неудачных;
- `spec.md`: букв и цифр, записей FR и ответ `check` (последние два — только с расширением).

Чтобы показатели считались без суждений, `dialog.md` ведётся в одном виде: заголовок `## Реплика N`, затем строки «Пользователь:» и «Исполнитель:» с текстом дословно; ответ вне роли помечается `[вне роли]` в начале реплики пользователя.

`start.md` — стартовый текст исполнителя, одинаковый у любого ведущего. Две части.

Среда — во всех вариантах:
- как задать вопрос с вариантами: в стенде `AskUserQuestion` — это блок в конце ответа по образцу из `start.md` (заголовок `AskUserQuestion`, вопрос, нумерованные варианты). Вид блока один у любого ведущего, поэтому прогоны сравнимы, и видно, задаёт ли исполнитель выбор через инструмент или перечисляет варианты в тексте;
- отдельный агент: умеешь запускать помощника — запускай его той же младшей моделью в чистом контексте; не умеешь — отдельного агента нет.

Расширение — только с ним:
- полный текст `rules/spec-forge.md`;
- как вызвать `spec_forge`: готовая команда `call` с путём стенда;
- что делать по команде `/spec-forge:sf-…`: прочитать `SKILL.md` этого скилла по указанному пути.

Тесты скриптов — в `tools/tests/`, по правилам [tools/README.md](../../tools/README.md):
- состав стенда после `prepare` в обоих вариантах, включая то, чего в нём нет;
- копия расширения из заданной версии, а не из рабочей папки;
- строка журнала после `call`, включая вызов с ошибкой и вызов без расширения;
- показатели и состав `report.md` после `collect`;
- отказ `compare` для несравнимой пары и состав `compare.md`, где нет ни варианта, ни версии сторон.

### Порядок прогона — `tools/model-run/README.md`

Тексты для ведущего и судьи. Они и есть результат работы, как тексты скиллов: составляются вместе с владельцем в PR. Что в них должно быть.

Прогон — ведущий:

1. Выполни `prepare`. Запусти исполнителя младшей моделью своего семейства в чистом контексте и передай ему `start.md` и первую реплику. С расширением — `/spec-forge:sf-grill` и текст `request.md`. Без расширения — текст `request.md` и текст `bare.md`.
2. Продолжай одного и того же исполнителя, пока сценарий не пройден. Не можешь продолжать — запускай нового с полным диалогом и запиши это в `meta.json`: такие прогоны сравниваются отдельно. Туда же запиши, мог ли исполнитель запускать помощников.
3. Отвечай только по `user.md`. Ответа в роли нет — отвечай «на твоё усмотрение, выбери рекомендованное» и пометь реплику `[вне роли]`. На блок `AskUserQuestion` отвечай номером варианта или своим текстом, как ответил бы пользователь в окне.
4. Не подсказывай: не называй следующий шаг, не поправляй ошибки, не напоминай о `check`. Исполнитель застрял — ответь «продолжай», не больше трёх раз подряд, затем останови прогон и запиши, где он встал.
5. После каждой реплики дописывай её в `dialog.md` стенда в принятом виде.
6. С расширением сценарий проходит цепочку `sf-grill` → `sf-spec` → `sf-review` → одобрение, если в `user.md` не сказано остановиться раньше. Без расширения — пока исполнитель не запишет `spec.md` и не скажет, что закончил.
7. Выполни `collect` и заполни раздел «Замечания». Документы, скиллы и правила не правь.

Обе стороны пары можно гонять одновременно: стенды не пересекаются.

Сравнение — судья в чистом контексте:

1. Получает `compare.md` и `user.md`, но не `key.json` и не стенды.
2. По каждому пункту «На что смотреть» выносит вердикт: «Первый лучше», «Второй лучше» или «Одинаково» — с цитатой из `compare.md` в подтверждение. Пункты части «Инструмент» в паре с прогоном без расширения не оцениваются.
3. Пишет общий вывод одной-двумя фразами и отдельно — что в паре могло решить случайное поведение модели.
4. Владелец открывает `key.json` только после вердикта.

В паре с прогоном без расширения вид документов выдаёт сторону, поэтому вслепую судить нельзя. Судья об этом предупреждён и судит по содержанию.

### Замечания в отчёте

```markdown
### Замечание 1
- Место: реплика 4, вызов 7
- Вид: неясная инструкция
- Что произошло: исполнитель спросил имя папки дважды.
- Цитата: «…»
```

Вид — один из четырёх: неясная инструкция, ошибка модели, ошибка инструмента, особенность стенда. Последний — для расхождений, которых в GigaCode не было бы. Цитата — дословно из диалога, журнала или документа.

## Работы

Каждая работа — отдельный PR в main.

1. **Инструмент и первый сценарий.** `run.mjs` и `compare.mjs` с тестами, `bare.md`, `README.md` с порядком прогона и сравнения, сценарий из раздела «Первый сценарий», раздел в `tools/README.md`. Один PR: это инструмент разработки. Стенды, отчёты и сравнения живут во временных папках вне репозитория.
2. **Первая пара и правки порядка.** Пара «без расширения — расширение из main» на первом сценарии: она проверяет оба варианта стенда и сразу даёт первый ответ, помогает ли инструмент на простой задаче. Всё, что в порядке прогона и сравнения оказалось неясным ведущему или судье, правится в `README.md`. Замечания к расширению в этот PR не входят: владелец поручает их отдельно.
3. **Прогон в GigaCode в том же виде.** Владелец запускает его сам на компьютере с GigaCode, где нет Claude и Codex, и только GigaCode. Сценарии — те же папки, варианты те же: без расширения и с расширением из заданной версии. Строка журнала, `report.md` и `meta.json` — того же вида, что в работе 1, поэтому `compare` и судья работают без изменений.
   - Журнал вызовов `spec_forge` пишет MCP-сервер: аргументы и ответ каждого вызова, только когда задан путь к файлу журнала в переменной окружения; иначе сервер ничего не пишет. Это новая пишущая обязанность, поэтому сначала правка «Что можно писать» в [design.md](design.md), затем критерии и реализация по AGENTS.md.
   - Пользователя играет скрипт по сценарию: реплики по смыслу, без номеров вопросов. Следующая реплика отправляется по условию на журнал или файлы задачи, например «`status` показал переход» или «появился `spec.md`». Реплика «продолжай» повторяется, пока условие не выполнено, но не больше заданного числа раз. Какой файл сценария хранит такие реплики, решается с владельцем в начале работы.
   - Ход — `gigacode -p` для новой сессии или `gigacode --resume <id> -p`, с `--approval-mode auto-edit --output-format json -m <модель>` и бюджетом ходов и времени. `session_id` берётся из вывода. Коды возврата 53 (исчерпаны ходы) и 55 (бюджет) попадают в отчёт.
   - Стенд — тот же, плюс `.gigacode/settings.json`: вызовы `spec_forge` разрешены в `permissions.allow`, запись истории не выключена.
   - Узнать первым прогоном: срабатывают ли `/spec-forge:sf-…` внутри `-p`; доходит ли переменная окружения до MCP-сервера; проходит ли запуск отдельного агента без подтверждения.

## Первый сценарий — `audit-role-filter`

Простая задача. Источников нет: папки `project/` у сценария нет.

### `request.md`

```markdown
В уже существующем журнале аудита нужен новый фильтр для поиска — «Роль пользователя». Фильтр ограничивает журнал: остаются только записи по пользователям с выбранной ролью. Список ролей хранится на сервере, получаем по REST. Допустим множественный выбор.
```

### `user.md`

```markdown
# Роль

Ты аналитик. Готовишь бизнес-требования, чтобы согласовать поведение с заказчиком и показать разработчикам. Кода и документации под рукой нет: источников для изучения не называй. На технические вопросы отвечай: «Не знаю, это к разработчикам».

# Ответы

- Имя папки: `audit-role-filter`.
- Где фильтр: только на экране журнала аудита, другие экраны не меняются.
- Кому доступен: всем, кто видит журнал; отдельного права нет.
- Что в списке: все роли из справочника, в том числе те, по которым записей нет.
- Несколько ролей выбрано: запись остаётся, если у пользователя есть хотя бы одна из них.
- У пользователя несколько ролей: достаточно одной совпавшей.
- Какая роль учитывается: та, что у пользователя сейчас, а не на момент записи.
- Записи без пользователя (действия системы): при выбранной роли скрываются.
- Ни одна роль не выбрана: журнал показывается как раньше.
- Вместе с другими фильтрами журнала: действуют одновременно.
- Список ролей не загрузился: журнал работает как обычно, фильтр по ролям недоступен.
- Ничего не найдено: то же сообщение, что журнал показывает сейчас при пустом результате.
- Сброс: существующая кнопка сброса фильтров журнала снимает и выбранные роли.
- Сохранение выбора: пока журнал открыт; при новом открытии фильтр пуст.
- Не входит в задачу: изменение ролей и справочника, другие экраны.
```

### `bare.md` — чистый запрос

```markdown
Составь по этой идее требования. Что неясно — спроси меня. Итог запиши в `docs/<имя сценария>/spec.md`.
```

`prepare` подставляет имя сценария. Запрос намеренно не говорит, что требования бизнесовые: так пара отвечает, что даёт инструмент целиком. Гипотеза «помогает ли инструмент сверх одной фразы о назначении» — отдельный чистый запрос, если владелец решит её проверить.
