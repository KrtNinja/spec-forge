# Проверка правок блока 7 повторным прогоном

Временный документ: удаляется после блока 7. Поручение агенту — «Проверь правки блока 7 по docs/core/run-check.md».

Прогон проверяет правки 1–4 из блока 7 `steps.md` на модели и то, что прежнее поведение не сломано. Модель — Claude Haiku, GigaCode изображается текстом сессии. Запускать после того, как реализация влита в `criteria/block-7` и проходят `npm --prefix tools test` и `npm --prefix tools run check`.

Нужно: запуск отдельных агентов на модели Haiku и продолжение их следующим сообщением (в Claude Code — `Agent` и `SendMessage`), Node 22.5.1. Ничего в репозитории не меняй.

## Как устроен прогон

- Ты играешь пользователя. Сессия GigaCode — агент на Haiku с текстом сессии из раздела ниже. Его итоговое сообщение — то, что видит пользователь; ответ пользователя — следующее сообщение тому же агенту. `/clear` — новый агент.
- `spec_forge` агент вызывает командой оболочки через обёртку `sf.mjs`. Она запускает `server/mcp.mjs` из папки образца и пишет каждый вызов с ответом в журнал. Журнал — главный источник: что агент передал инструменту и что увидел пользователь.
- Отдельный агент изображается так: основной агент заканчивает сообщение строкой `ПОРУЧЕНИЕ ОТДЕЛЬНОМУ АГЕНТУ:` и заданием. Ты запускаешь нового агента на Haiku с текстом «отдельный агент» и этим заданием дословно, а его отчёт передаёшь основному агенту следующим сообщением с пометкой «[Отдельный агент закончил работу. Его отчёт:]».

## Стенд

R — корень репозитория на ветке `criteria/block-7`, W — пустая временная папка вне репозитория.

1. Образец проекта `W/project`: три файла, `git init` и первый коммит.

   `src/auth/login.js`:
   ```js
   // Вход по логину и паролю.
   import { findUser, checkPassword, issueToken } from './users.js';

   export async function login(name, password) {
     const user = await findUser(name);
     if (!user || !(await checkPassword(user, password))) {
       return { ok: false, message: 'Неверный логин или пароль' };
     }
     return { ok: true, token: issueToken(user) };
   }
   ```

   `src/auth/users.js`:
   ```js
   // Пользователи хранятся в таблице users: name, password_hash, role (customer | operator | admin).
   export async function findUser(name) { /* запрос к базе */ }
   export async function checkPassword(user, password) { /* сравнение хеша */ }
   export function issueToken(user) { /* токен сессии на 30 дней */ }
   ```

   `wiki/auth-policy.md`:
   ```markdown
   # Правила входа

   - Пароль не короче 8 знаков.
   - Сессия действует 30 дней.
   - Операторы и администраторы входят в ту же форму, что и покупатели.
   - Пароль сбрасывается по ссылке из письма; служба поддержки может отправить ссылку по звонку клиента.
   ```

   Файла `W/shared/security-policy.md` нет: это недоступный источник.

2. Обёртка `W/sf.mjs`:
   ```js
   // node sf.mjs '<JSON>' из папки проекта: вызывает spec_forge и пишет вызов в журнал.
   import { spawn } from 'node:child_process';
   import { appendFileSync } from 'node:fs';
   import { join } from 'node:path';

   const { SF_ROOT, SF_LOG, SF_WHO = '?' } = process.env;
   let args;
   try {
     args = JSON.parse(process.argv[2] ?? '');
   } catch {
     console.log('Аргументы spec_forge — JSON одной строкой в одинарных кавычках.');
     process.exit(1);
   }
   const child = spawn(process.execPath, [join(SF_ROOT, 'server/mcp.mjs')], { stdio: ['pipe', 'pipe', 'inherit'] });
   let out = '';
   let done = false;
   child.stdout.on('data', (chunk) => {
     out += chunk;
     const end = out.indexOf('\n');
     if (end < 0 || done) return;
     done = true;
     const { result = {}, error } = JSON.parse(out.slice(0, end));
     const text = (result.content ?? []).map((c) => c.text).join('\n') || JSON.stringify(error);
     const shown = result.isError ? `Вызов не удался:\n${text}` : text;
     appendFileSync(SF_LOG, `\n#### [${SF_WHO}] spec_forge ${JSON.stringify(args)}\n\n${shown}\n`);
     console.log(shown);
     child.kill();
   });
   const call = { jsonrpc: '2.0', id: 1, method: 'tools/call', params: { name: 'spec_forge', arguments: args } };
   child.stdin.write(`${JSON.stringify(call)}\n`);
   ```

   Команда вызова для текста сессии, с настоящими путями: `cd W/project && SF_ROOT=R SF_LOG=W/log.md SF_WHO=<сессия> node W/sf.mjs '<аргументы JSON одной строкой>'`. Проверь её сам вызовом `{"action":"status","command":"sf-grill"}` и удали получившийся журнал.

## Текст сессии

Собери из частей, подставив пути:

1. «Ты — агент в GigaCode CLI и работаешь с пользователем над проектом в папке W/project. В GigaCode установлено расширение Spec Forge. Твой итоговый ответ — это сообщение пользователю; закончив его, остановись: ответ придёт следующим сообщением. Ответы за пользователя не выдумывай. Работай только в папке проекта. Инструмента выбора вариантов в этой сессии нет.»
2. Агент есть: «Инструмент запуска отдельного агента в этой среде — такая запись: закончи сообщение строкой `ПОРУЧЕНИЕ ОТДЕЛЬНОМУ АГЕНТУ:` и ниже — полный текст задания; когда агент закончит, придёт сообщение. Другими инструментами запуска агентов не пользуйся.» Агента нет: «Инструмента запуска отдельного агента в этой сессии нет. Инструменты запуска агентов, которые ты видишь, к этой среде не относятся — не пользуйся ими.» Так признак `agent` в стенде означает то же, что в GigaCode: есть ли инструмент запуска.
3. Инструмент `spec_forge`: команда вызова; «Пользователь видит ответ инструмента целиком»; описание и описание каждого поля — из `tool` в `server/contract.mjs`.
4. Скиллы: для каждого `skills/*/SKILL.md` — имя, путь к файлу и `description` из заголовка. «Когда пользователь пишет `/имя …` или ты сам решаешь запустить скилл, прочитай его файл целиком и следуй ему; текст после команды — аргументы. Другие файлы в R не читай.»
5. Правила: текст `rules/spec-forge.md` без заголовка `paths`.
6. «Первое сообщение пользователя» и само сообщение.

Отдельный агент получает части 3–5, перед ними — «Ты — отдельный агент в GigaCode CLI. Выполни задание основного агента и закончи кратким отчётом. Работай только в папке W/project. Свой инструмент запуска агентов не используй.», после них — задание основного агента дословно.

## Ситуации

Сессии идут подряд на одном образце. В скобках — правка из `steps.md`, которую проверяет пункт.

### Сессия A — агент есть

Первое сообщение: `/sf-grill Хочу временно блокировать вход после нескольких неудачных попыток ввода пароля. Код входа — в src/auth/, правила — в wiki/auth-policy.md и ../shared/security-policy.md`

Ответы пользователя:
- имя папки — сначала `блокировка-входа`, после просьбы — `login-lock`;
- недоступный источник — «продолжай без него»;
- число попыток до блокировки — «не знаю, спрошу у службы безопасности»; остальное — рекомендуемые варианты;
- агент сказал, что вопросов больше нет, — `/sf-note Служба безопасности ответила: блокировать после 5 неудачных попыток подряд`;
- подготовить требования — «В этой сессии»; новые вопросы `sf-spec` — коротко, по здравому смыслу;
- «Проверить требования» или «Одобрить» — «Проверить требования»;
- блокирующие замечания — «принять»; из остальных одно «отложить» (ответ — следующим `/sf-note`), прочие «принять»;
- ответ на отложенное — `/sf-note …`, затем «Одобряю».

Ожидается:
- (2) поручение на изучение содержит задание из ответа `status` целиком, включая «Каждый источник запиши так, как он записан выше»;
- (2) в «Изучено» `_work/context.md` есть пункт `src/auth/`, и `status` после изучения не называет его недоступным;
- (3) каждый вызов `status` с `sf-review` в этой сессии — `touched: true` и `agent: true`;
- после разбора замечаний `status` с `sf-review` по-прежнему предлагает «Повторить проверку требований» или «Одобрить»: правка 1 этого не меняет;
- агент ждал решения по недоступному источнику (FR-27); блокирующий вопрос закрывал переход до ответа; одобрение — строкой из `check`, затем сообщение об одобрении.

### Сессия B — агента нет

Сообщения по очереди:
1. `/sf-note login-lock Бизнес подтвердил, что срок блокировки 15 минут — окончательный, менять его не будут.`
2. `/sf-note login-lock Служба безопасности передумала: блокировать на 30 минут, а не на 15.`
3. `Проверить требования`

Ожидается:
- (4) после 1 нового `Q-…` нет; `spec.md` не изменён, `check` подтверждает одобрение;
- (4) после 2 нового `Q-…` нет, у вопросов в `questions.md` нет полей не из образца; прежнее решение помечено «Заменено», FR поправлены, «Статус: черновик»;
- (3) после 3 — `status` с `touched: true` и `agent: false`, ответ — только новая сессия (FR-17).

### Сессия C — агент есть

Первое сообщение: `/sf-review login-lock`

Ожидается:
- (1) первый `status` — `touched: false`, ответ — «проверить требования — здесь, в этой сессии», без «Одобрить»; агент проверяет сразу, без встречного вопроса, и дописывает раздел в `_work/review.md`;
- (3) после проверки `status` — `touched: true` и `agent: true`.

Замечания — «принять», затем «Одобряю».

## Итог

Ответ владельцу: по каждому пункту «Ожидается» — выполнено или нет; для невыполненного — выдержка из журнала и сообщение агента. Отдельно — новые странности, если заметил. Журнал приложи файлом. Если пункты (3) выполнены не во всех вызовах, повтори сессии A–C ещё раз и назови долю верных вызовов: эти признаки модель сообщает нестабильно.
