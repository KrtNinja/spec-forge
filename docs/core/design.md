# Общее устройство Spec Forge

Как выполнены требования [основы](../product-requirements.md): инструмент, форматы документов, переходы, проверки. Путь пользователя описан в основе, устройство отдельных этапов — в `design.md` их папок. Все разделы согласованы с владельцем.

## Состав и подключение

```
gigacode-extension.json    имя расширения и MCP-сервер spec-forge:
                           node ${extensionPath}/server/mcp.mjs
rules/spec-forge.md        общие правила и образцы записей D и Q
skills/sf-grill/SKILL.md   вместе с текстом grilling
skills/sf-grill/LICENSE-grilling
skills/sf-spec/SKILL.md
skills/sf-review/SKILL.md
skills/sf-note/SKILL.md
server/                    MCP-сервер и логика без зависимостей
server/contract.mjs        договор: описание и схема инструмента, форматы документов
server/texts.mjs           тексты ответов
tests/                     критерии: случаи вызова, обмен с сервером, состав расширения
tools/                     проверки разработки
```

Подключение: `gigacode extensions link <папка расширения>`. MCP-сервер обменивается с GigaCode через стандартный ввод и вывод и работает без npm-пакетов. Пользователю ничего устанавливать не нужно, а путь к скрипту не попадает в команды оболочки, которые выполняет агент. Запросы обрабатываются и без начального `initialize`: в спецификации MCP от 2026-07-28 он убран. Точные правила обмена — в `tests/protocol.test.mjs`.

Команд четыре: `sf-grill`, `sf-spec`, `sf-review`, `sf-note`. Отдельных команд «продолжить» и «одобрить» нет:
- любой скилл продолжает с места, которое назвал `status`;
- ответ бизнеса или разработчика приходит через `sf-note`;
- одобрить предлагает агент, когда `check` сообщил, что условия выполнены.

Скиллы доступны модели для вызова. Это нужно, чтобы продолжить в текущей сессии по FR-13, распознать новые сведения по FR-24 и перейти к проверке требований: `sf-spec` передаёт её скиллу `sf-review` в той же сессии, а путь проверки выбирает тот ([sf-review/design.md](../sf-review/design.md)).

Первый шаг каждого скилла: вызвать `spec_forge` с действием `status`, а если инструмента не видно — найти его через поиск инструментов (FR-28). Эта строка повторяется во всех четырёх скиллах. Правила из `rules/` в этот момент могут быть ещё не загружены.

## Детерминированный инструмент

**Сначала минимум записи.** Один MCP-инструмент `spec_forge` с полем `action`. Действий три:

| action | Что делает |
|---|---|
| `status` | Находит задачу: явно указанную, единственную подходящую или просит выбрать. Проверяет имя новой папки. Определяет этап, доступные действия и следующий шаг. Рекомендует сессию по FR-13. Выбирает путь проверки требований ([sf-review/design.md](../sf-review/design.md)). Проверяет источники и выдаёт задание на их изучение ([sf-grill/design.md](../sf-grill/design.md)) |
| `check` | Проверяет документы задачи (раздел «Проверки») и подсказывает следующие свободные номера. Если в `affected` переданы затронутые решения и вопросы, называет зависящие от них FR. Если сумма одобрения не совпадает, сообщает, что одобрение не действует ([sf-note/design.md](../sf-note/design.md)). Когда условия одобрения выполнены, выдаёт готовую строку статуса. Ничего не меняет |
| `link` | Превращает номера `D-…`, `Q-…`, `R-…`, `FR-…` без ссылки в ссылки с правильным файлом, путём и якорем. Чинит ссылку с ошибочной целью, если правильная цель однозначна, а неоднозначную только показывает. Больше ничего не меняет |

**Что можно писать.** `status` и `check` только читают и сообщают. `link` пишет только ссылки. Документы и записи ведёт модель по образцам, а ошибки формата ловит `check`. Новая пишущая обязанность — только новым действием и только вместе с правкой этого документа.

Модель пишет только номер, например «Основание: D-03». Что на что ссылается, решает она. Оформление ссылки по FR-25 — работа `link`. Номера не переиспользуются, файлы не переезжают, поэтому готовые ссылки не устаревают. Если решение заменено, `check` укажет FR, которые на него опираются, а перевод FR на новое решение — смысловая правка модели.

Как работает `link` в документах задачи:
- номер в тексте становится ссылкой с путём от документа до файла записи: `D-03` → `[D-03](brainstorming.md#d-03)`, `R-02` → `[R-02](_work/review.md#r-02)`, в `_work/review.md` — `[FR-01](../spec.md#fr-01)`, в своём файле — только якорь `#d-03`. Номер в обратных апострофах становится текстом ссылки вместе с ними;
- заголовки, блоки кода, строки до первого заголовка, пути с номером и ссылки с другим текстом не меняются;
- ссылку, у которой текст — номер записи, а адрес ведёт не на эту запись, `link` исправляет;
- номер, которого нет среди записей, остаётся как есть — его покажет `check`. Номер у нескольких записей тоже остаётся, а место показывается в «Не исправлено», по одному разу на запись или раздел;
- сначала читаются все документы, затем меняются только изменившиеся; переводы строк файла сохраняются. Ответ — «Ссылок проставлено: N, исправлено: M.».

Разрешить вызов MCP в GigaCode достаточно один раз на сессию.

### Ответ инструмента

Пользователь видит ответ инструмента целиком, поэтому ответ пишется для человека. Описание и схема инструмента — в договоре `server/contract.mjs`, все тексты ответов — в `server/texts.mjs`. Указание агенту формулируется так, чтобы и человеку было понятно, например «Дальше: `/sf-spec order-search`». JSON и служебного формата, как в sdd-planner, нет.

Если документ задачи не читается — это папка или нет прав, — вызов не удаётся с именем этого документа, а сервер продолжает работу.

Объём ответа:
- `check` без ошибок — одна строка, например «Ошибок нет. Следующие номера: D-06, Q-03.»; есть `spec.md` — в строке и следующий `FR`, есть `_work/review.md` — и `R`;
- ошибки — список «где — что» и та же строка номеров;
- переданы затронутые записи — после строки номеров список: по пункту на номер с зависящими FR;
- есть `spec.md` — затем абзацами: предупреждение о размере, затем, если ошибок нет, одобрение: готовая строка, открытые вопросы, сообщение об одобрении или «сумма не совпадает»;
- `status` — 2–4 строки: задача, этап, что дальше;
- `status` с заданием на изучение — дополнительно само задание, около 10 строк. Пользователь видит, что поручается отдельному агенту, а для другого окна копирует этот текст;
- `status` с путём проверки «отдельным агентом» — дополнительно короткое задание на проверку.

Оформление в Markdown:
- абзацы и блоки разделяются пустой строкой — одиночный перенос строки склеивает текст в сплошной абзац;
- перечни начинаются с «- », каждый пункт на своей строке;
- команды, имена файлов и номера записей пишутся в обратных апострофах;
- заголовок блока выделяется жирным на отдельной строке;
- строка «Tip: Введите … чтобы продолжить» идёт последней и без оформления.

Агент не пересказывает ответ инструмента: пользователь его уже видел.

## Документы задачи

Папка задачи — `docs/<имя>/`. Номера записей пишутся латиницей: `FR`, `D` (решение), `Q` (вопрос), `R` (замечание проверки). Кириллическая «Р» и латинская «P» выглядят одинаково, и модель их путает. Заголовки и текст пишутся по-русски.

Заголовок каждой записи состоит только из номера, например `### D-03`, а текст идёт под ним. Тогда якорь однозначен: `#d-03`. Номер — две цифры и больше, без лишних нулей впереди: `D-01`, `D-99`, `D-100`. Нумерация каждого вида сквозная по задаче, в том числе `R` между разделами `review.md`. Следующий номер — наибольший плюс один. Поле записи — пункт «- Поле: значение»; «Решение» у `D-…` и каждое поле `Q-…` и `R-…` — не больше одного раза.

| Файл | Содержимое |
|---|---|
| `brainstorming.md` | `## Запрос`; `## Источники` — каждая строка — пункт, который начинается с пути в обратных апострофах или со ссылки, подзаголовков нет, нет источников — раздел пустой; `## Решения` — записи `D-…`: «Вопрос», «Рекомендация» агента, «Решение» пользователя, заменённое решение не удаляется, а получает поле «Заменено: D-…», ответ на вопрос — решение с номером вопроса; `## Не входит в задачу`. Каждый раздел — ровно один раз |
| `questions.md` | `Q-…`: текст вопроса, «Этап» (команда), «Блокирует» (да / нет), «Помощь» — чья нужна, «Статус» (открыт / решён / не входит), «Ответ». Вопрос «не входит» упоминается в разделе «Не входит в задачу» файла `brainstorming.md`, в том числе в его подзаголовке |
| `spec.md` | Строка статуса; `## Цель`; `## Требования` — записи `FR-…`: правило текстом, «Пример» одной строкой, «Основание» — номера решений `D-…` через запятую; `## Не входит в задачу`; ссылка на `questions.md`, если он есть. Каждый раздел — ровно один раз |
| `_work/review.md` | Разделы проверок — заголовки второго уровня; каждая проверка дописывает свой раздел в конец. В разделе — `R-…`: «Важность» (блокирует / замечание), «Где», «Проблема», «Рекомендация» и «Решение» (принято / своё решение / отложено / отклонено, по FR-19); пустое «Решение» — замечание не разобрано. Номер отложенного замечания упомянут хотя бы в одном вопросе `Q-…` в `questions.md`. Учитывается последний раздел: после последнего заголовка первого или второго уровня |
| `_work/context.md` | `## Источники` с подразделами `### Изучено` и `### Не изучено` (с причиной), `## Факты` (каждый факт с источником), `## Противоречия`, `## Не найдено`. Каждый заголовок — ровно один раз |

Строка статуса `spec.md` — строка вне блоков кода, которая начинается со «Статус:», ровно одна; пробелы в конце не учитываются. Она принимает два вида:
- «Статус: черновик» — до одобрения и после изменения смысла;
- «Статус: одобрено 2026-11-06 · a1b2c3» — сегодняшняя дата по часам компьютера и первые шесть знаков SHA-256 содержимого без строки статуса. Перед подсчётом текст приводится к одному виду: окончания строк — LF, без пробелов в конце строк и без пустых строк в конце файла. Так сумма не меняется от переноса файла между системами или случайного пробела.

Образцы записей лежат там, где ими пользуются:
- образцы `D-…` и `Q-…` — в `rules/spec-forge.md`, потому что их пишут несколько скиллов;
- образец FR — только в `sf-spec`;
- образец `R-…` — только в `sf-review`.

Порядок разделов документа задаёт образец, отдельного шаблона нет.

## Состояние и переходы

Отдельного файла состояния нет, этап вычисляется из документов. Строки таблицы проверяются сверху вниз, срабатывает первая подходящая.

| Условие | Доступный шаг |
|---|---|
| Нет папки задачи | Новая задача |
| Есть `brainstorming.md`, нет `spec.md` | Продолжить обсуждение. Если блокирующих вопросов нет — подготовить требования; иначе они перечисляются |
| Есть `spec.md`, проверки не пройдены | Исправить |
| Одобрено, в последнем разделе `review.md` блокирующее замечание без решения или отложенное | Одобрение не действует: «Статус: черновик», затем разбор и повторная проверка через `sf-review`. Сам процесс к этому не приводит: `check` не даёт одобрить, а одобренную задачу `sf-review` не проверяет |
| Одобрено, есть открытый вопрос | Ответ — через `sf-note`. Ответ меняет смысл требований — «Статус: черновик», правка `spec.md` и повторное одобрение |
| Одобрено, сумма не совпадает | Одобрение не действует: «Статус: черновик» и повторное одобрение (FR-24) |
| Одобрено, сумма совпадает | Работа завершена; новые сведения — через `sf-note` |
| В последнем разделе `review.md` есть блокирующее замечание без решения | Разбор блокирующих замечаний по одному |
| В последнем разделе `review.md` есть замечание без решения | Разобрать все, выбранные или отклонить (FR-18). Без рекомендации — повторить проверку требований или одобрить, если выполнены условия FR-21 (FR-20) |
| Проверки пройдены, проверки ИИ ещё не было | Проверить требования (рекомендуется) или одобрить, если выполнены условия FR-21 |
| Проверки пройдены, в `review.md` есть разобранный раздел | Повторить проверку требований или одобрить, без рекомендации (FR-20) |

Блокирующий вопрос — не «решён» и не «не входит», и в нём нет «Блокирует: нет». Вопрос без поля «Блокирует» или с неверным статусом считается блокирующим, а повторённое поле значения не имеет: ошибку оформления покажет `check`, а переход не откроется раньше времени.

Одобрение. Когда условия FR-21 выполнены, `check` выдаёт готовую строку «Статус: одобрено …». Ошибок нет, а вопросы открыты или блокирующие замечания не разобраны либо отложены — `check` называет их: одобрить нельзя. Модель вставляет строку только после явного решения пользователя. Затем она вызывает `check`, и тот выдаёт сообщение об одобрении по FR-22 со ссылкой Markdown на `spec.md`, а если есть `questions.md` — и на него, и предложением закоммитить папку задачи. Сообщение повторяется при каждом `check` одобренной задачи: инструмент не знает, был ли коммит. Есть такие препятствия — `check` одобрение не подтверждает и называет их, даже если строка одобрения уже стоит. Дословные слова пользователя не записываются.

Изменение одобренного документа описано в [sf-note/design.md](../sf-note/design.md).

## Контекст

- **Общие правила** (`rules/spec-forge.md`): правило языка; решения принимает пользователь; после правки документов задачи Spec Forge вызвать `link`, затем `check`; ответ инструмента не пересказывать; неудачный вызов `spec_forge` не выдавать за выполненный (FR-28); образцы записей `D-…` и `Q-…`.
- **По вызову:** тело текущего скилла и ответ инструмента со следующим шагом.

Правило языка из основы — одно общее правило в `rules/spec-forge.md`, без повторения в каждом скилле.

Предел для `rules/spec-forge.md` и каждого `SKILL.md` — 10 000 букв и цифр; превышение — ошибка проверки.

Правила подключаются не через `contextFileName`, а заголовком `paths: ["**/docs/**"]` в начале файла, как предлагает GigaCode. Они загружаются только при работе с документацией, а не во всех сессиях.

Чтобы правила оказались в контексте до первого ответа, после `status` скилл читает документы задачи. Какие именно — указано в устройстве каждого этапа.

## Вход в работу и выбор задачи

- `status` получает команду входа в поле `command` и задачу в поле `task`: существующую или имя новой папки, без пути `docs/`. Пустое `task` — то же, что без него. Для `sf-review` модель передаёт ещё признаки `touched` и `agent` ([sf-review/design.md](../sf-review/design.md)); без них вызов не удаётся.
- Указана ли задача в команде или это описание идеи, определяет модель. `status` проверяет, что названная задача существует.
- Задача — папка в `docs/` с `brainstorming.md`. Другие папки `docs/` задачами не считаются.
- Без `task` `status` ищет подходящие задачи: нет — новая задача, одна — продолжить её, несколько — выбрать.
- Подходящая задача — та, где эта команда сейчас доступна:
  - `sf-grill` — задача без `spec.md`;
  - `sf-spec` — задача с `brainstorming.md`, ещё не одобренная;
  - `sf-review` — задача с `spec.md`, ещё не одобренная;
  - `sf-note` — любая задача, включая одобренные.
- Новую задачу начинает только `sf-grill` ([sf-grill/design.md](../sf-grill/design.md)).
- Названной задаче команда не подходит — `status` отправляет к подходящей со строкой Tip: `sf-grill` для задачи со `spec.md`, ещё не одобренной, — к `sf-spec`; `sf-spec` для задачи, где обсуждение не закончено, — к `sf-grill` ([sf-spec/design.md](../sf-spec/design.md)); `sf-review` для задачи без `spec.md` — к `sf-spec`. Для одобренной задачи все команды отвечают одинаково.
- `sf-note` отвечает как команда этапа задачи: без `spec.md` — как `sf-grill`, со `spec.md` — как `sf-spec` ([sf-note/design.md](../sf-note/design.md)).

## Переходы между сессиями

Новая сессия в GigaCode — это `/clear` или перезапуск окна. Инструмент показывает оба способа и команду продолжения, например `/sf-spec <имя>` или `/sf-review <имя>` для проверки в новой сессии. Последняя строка ответа — «Tip: Введите /sf-spec <имя> чтобы продолжить», без кавычек и обратных апострофов: по ней GigaCode подставляет команду в строку ввода. Строка Tip печатается только вместе с переходом: её нет, пока переход закрыт, например блокирующими вопросами, и когда задачу выбирает пользователь. Закончено ли обсуждение, решает модель, поэтому переход показывается при каждом `status`, пока он доступен.

## Проверки

Ошибки:
- обязательные разделы документов; `_work/context.md` проверяется, только если он есть;
- в «Источниках» `brainstorming.md` строка не пункт с источником в начале или подзаголовок: такие источники `status` не видит;
- в «Решениях», в `questions.md` и под разделами `_work/review.md` заголовок не номер; формат и уникальность номеров;
- у решения не заполнено «Решение»; поле записи повторяется;

- цели ссылок существуют: упомянутые номера `D-…`, `Q-…`, `FR-…` и `R-…` есть среди записей; для ссылки в тупик указывается запись или раздел, где она стоит. Номер упоминается в тексте и в заголовке раздела, кроме заголовка записи; номер в пути или имени файла, например `D-07-api.md`, упоминанием не считается. Ссылка, у которой текст — номер записи, ведёт на эту запись; иначе её исправит `link`. Внешние адреса и якоря заголовков не проверяются;

Несовпадение суммы одобрения ошибкой проверки не считается: это условие перехода «Одобрено, сумма не совпадает», и снимает его только повторное одобрение.
