# Общее устройство Spec Forge

Как выполнены требования [основы](../product-requirements.md): инструмент, форматы документов, переходы, проверки. Путь пользователя описан в основе, устройство отдельных этапов — в `design.md` их папок. Все разделы согласованы с владельцем. Реализация не начата.

## Состав и подключение

```
gigacode-extension.json    имя расширения и MCP-сервер spec-forge:
                           node ${extensionPath}/server/mcp.mjs
rules/spec-forge.md        общие правила и образцы записей D и Q, около 1,5 КБ
skills/sf-grill/SKILL.md   вместе с текстом grilling
skills/sf-grill/LICENSE-grilling
skills/sf-spec/SKILL.md
skills/sf-review/SKILL.md
skills/sf-note/SKILL.md
server/                    MCP-сервер и логика без зависимостей
tools/                     проверки разработки, как сейчас
```

Подключение: `gigacode extensions link <папка расширения>`. MCP-сервер обменивается с GigaCode через стандартный ввод и вывод и работает без npm-пакетов. Пользователю ничего устанавливать не нужно, а путь к скрипту не попадает в команды оболочки, которые выполняет агент.

Команд четыре: `sf-grill`, `sf-spec`, `sf-review`, `sf-note`. Отдельных команд «продолжить» и «одобрить» нет:
- любой скилл продолжает с места, которое назвал `status`;
- ответ бизнеса или разработчика приходит через `sf-note`;
- одобрить предлагает агент, когда `check` сообщил, что условия выполнены.

Скиллы доступны модели для вызова. Это нужно, чтобы продолжить в текущей сессии по FR-13 и распознать новые сведения по FR-24. Исключение — `sf-review`, его путь проверки описан в [sf-review/design.md](../sf-review/design.md).

Первый шаг каждого скилла: вызвать `spec_forge` с действием `status`, а если инструмента не видно — найти его через поиск инструментов (FR-28). Эта строка повторяется во всех четырёх скиллах. Правила из `rules/` в этот момент могут быть ещё не загружены.

## Детерминированный инструмент

**Сначала минимум записи.** Один MCP-инструмент `spec_forge` с полем `action`. Действий три:

| action | Что делает |
|---|---|
| `status` | Находит задачу: явно указанную, единственную подходящую или просит выбрать. Проверяет имя новой папки. Определяет этап, доступные действия и следующий шаг. Рекомендует сессию по FR-13. Выбирает путь проверки требований ([sf-review/design.md](../sf-review/design.md)). Проверяет источники и выдаёт задание на их изучение ([sf-grill/design.md](../sf-grill/design.md)) |
| `check` | Проверяет документы задачи (раздел «Проверки») и подсказывает следующие свободные номера. Если переданы затронутые решения, возвращает зависящие от них FR. Если сумма одобрения не совпадает, показывает разницу с одобренной версией ([sf-note/design.md](../sf-note/design.md)). Когда условия одобрения выполнены, выдаёт готовую строку статуса. Ничего не меняет |
| `link` | Превращает номера `D-…`, `Q-…`, `R-…`, `FR-…` без ссылки в ссылки с правильным файлом, путём и якорем. Чинит ссылку с ошибочной целью, если правильная цель однозначна, а неоднозначную только показывает. Больше ничего не меняет |

**Что можно писать.** `status` и `check` только читают и сообщают. `link` пишет только ссылки. Документы и записи ведёт модель по образцам, а ошибки формата ловит `check`. Новая пишущая обязанность — только новым действием и только вместе с правкой этого документа.

Модель пишет только номер, например «Основание: D-03». Что на что ссылается, решает она. Оформление ссылки по FR-25 — работа `link`. Номера не переиспользуются, файлы не переезжают, поэтому готовые ссылки не устаревают. Если решение заменено, `check` укажет FR, которые на него опираются, а перевод FR на новое решение — смысловая правка модели.

Разрешить вызов MCP в GigaCode достаточно один раз на сессию.

### Ответ инструмента

Пользователь видит ответ инструмента целиком, поэтому ответ пишется для человека. Указание агенту формулируется так, чтобы и человеку было понятно, например «Дальше: `/sf-spec order-search`». JSON и служебного формата, как в sdd-planner, нет.

Объём ответа:
- `check` без ошибок — одна строка, например «Ошибок нет. Следующие номера: D-06, Q-03.»;
- ошибки — список «где — что»;
- `status` — 2–4 строки: задача, этап, что дальше;
- `status` с заданием на изучение — дополнительно само задание, около 10 строк. Пользователь видит, что поручается отдельному агенту, а для другого окна копирует этот текст;
- разница после одобрения показывается как есть: пользователю полезно видеть, что изменилось.

Оформление в Markdown:
- абзацы и блоки разделяются пустой строкой — одиночный перенос строки склеивает текст в сплошной абзац;
- перечни начинаются с «- », каждый пункт на своей строке;
- команды, имена файлов и номера записей пишутся в обратных апострофах;
- заголовок блока выделяется жирным на отдельной строке;
- строка «Tip: Введите … чтобы продолжить» идёт последней и без оформления.

Агент не пересказывает ответ инструмента: пользователь его уже видел.

## Документы задачи

Папка задачи — `docs/<имя>/`. Номера записей пишутся латиницей: `FR`, `D` (решение), `Q` (вопрос), `R` (замечание проверки). Кириллическая «Р» и латинская «P» выглядят одинаково, и модель их путает. Заголовки и текст пишутся по-русски.

Заголовок каждой записи состоит только из номера, например `### D-03`, а текст идёт под ним. Тогда якорь однозначен: `#d-03`. Нумерация каждого вида сквозная по задаче, в том числе `R` между разделами `review.md`.

| Файл | Содержимое |
|---|---|
| `brainstorming.md` | Запрос, источники, решения `D-…` (слова пользователя отдельно от рекомендации агента; заменённое решение не удаляется, а помечается «заменено D-…»; ответ на вопрос `Q-…` оформляется решением `D-…` со ссылкой на вопрос), «Не входит в задачу» |
| `questions.md` | `Q-…`: этап, блокирует (да/нет), чья помощь нужна, статус (открыт / решён / не входит), ответ. Вопрос «не входит» упоминается в разделе «Не входит в задачу» файла `brainstorming.md` |
| `spec.md` | Строка статуса, цель, `FR-…` (поведение, пример, «Основание: D-…»), границы, ссылка на `questions.md` |
| `_work/review.md` | Разделы проверок. В разделе — `R-…`: важность (блокирует / замечание), где, проблема, рекомендация, решение (принято / своё решение / отложено / отклонено, по FR-19). Учитывается последний раздел |
| `_work/context.md` | Разделы «Факты» (каждый с источником), «Противоречия», «Не найдено» |

Строка статуса `spec.md` принимает два вида:
- «Статус: черновик» — до одобрения и после изменения смысла;
- «Статус: одобрено 2026-11-06 · a1b2c3» — дата и короткая контрольная сумма содержимого без строки статуса. Перед подсчётом текст приводится к одному виду: окончания строк — LF, без пробелов в конце строк и без пустых строк в конце файла. Так сумма не меняется от переноса файла между системами или случайного пробела.

Образцы записей лежат там, где ими пользуются:
- образцы `D-…` и `Q-…` — в `rules/spec-forge.md`, потому что их пишут несколько скиллов;
- образец FR — только в `sf-spec`;
- образец `R-…` — только в `sf-review`.

Порядок разделов документа задаёт образец, отдельного шаблона нет.

## Состояние и переходы

Отдельного файла состояния нет, этап вычисляется из документов. Строки таблицы проверяются сверху вниз, срабатывает первая подходящая.

| Условие | Доступный шаг |
|---|---|
| Нет папки задачи | Новая задача |
| Есть `brainstorming.md`, нет `spec.md` | Продолжить обсуждение. Если блокирующих вопросов нет — подготовить требования |
| Есть `spec.md`, проверки не пройдены | Исправить. Для одобренной задачи оценка разницы — после исправления |
| Одобрено, есть открытый вопрос | Ответ — через `sf-note`. После ответа агент оценивает, изменился ли смысл |
| Одобрено, сумма не совпадает | Агент оценивает разницу: правка без смены смысла или повторное одобрение |
| Одобрено, сумма совпадает | Работа завершена; новые сведения — через `sf-note` |
| В последнем разделе `review.md` есть блокирующее замечание без решения | Разбор блокирующих замечаний по одному |
| В последнем разделе `review.md` есть замечание без решения | Разобрать все, выбранные или отклонить (FR-18). Без рекомендации — повторить проверку требований или одобрить, если выполнены условия FR-21 (FR-20) |
| Проверки пройдены, проверки ИИ ещё не было | Проверить требования (рекомендуется) или одобрить, если выполнены условия FR-21 |
| Проверки пройдены, в `review.md` есть разобранный раздел | Повторить проверку требований или одобрить, без рекомендации (FR-20) |

Одобрение. Когда условия FR-21 выполнены, `check` выдаёт готовую строку «Статус: одобрено …». Модель вставляет её только после явного решения пользователя. Затем она вызывает `check`, и тот выдаёт сообщение об одобрении по FR-22. Дословные слова пользователя не записываются.

Изменение одобренного документа описано в [sf-note/design.md](../sf-note/design.md).

## Контекст

- **Общие правила** (`rules/spec-forge.md`, около 1,5 КБ вместе с образцами): правило языка; решения принимает пользователь; после правки документов задачи Spec Forge вызвать `link`, затем `check`; ответ инструмента не пересказывать; образцы записей `D-…` и `Q-…`.
- **По вызову:** тело текущего скилла и ответ инструмента со следующим шагом.

Правило языка из основы — одно общее правило в `rules/spec-forge.md`, без повторения в каждом скилле.

Правила подключаются не через `contextFileName`, а заголовком `paths: ["**/docs/**"]` в начале файла, как предлагает GigaCode. Они загружаются только при работе с документацией, а не во всех сессиях.

Чтобы правила оказались в контексте до первого ответа, после `status` скилл читает документы задачи. Какие именно — указано в устройстве каждого этапа.

## Вход в работу и выбор задачи

- Указана ли задача в команде или это описание идеи, определяет модель. `status` проверяет, что названная задача существует.
- Подходящая задача — та, где эта команда сейчас доступна:
  - `sf-grill` — задача без `spec.md`;
  - `sf-spec` — задача с `brainstorming.md`, ещё не одобренная;
  - `sf-review` — задача с `spec.md`, ещё не одобренная;
  - `sf-note` — любая задача, включая одобренные.
- Новую задачу начинает только `sf-grill` ([sf-grill/design.md](../sf-grill/design.md)).

## Переходы между сессиями

Новая сессия в GigaCode — это `/clear` или перезапуск окна. Инструмент показывает оба способа и команду продолжения, например `/sf-spec <имя>`. Последняя строка ответа — «Tip: Введите /sf-spec <имя> чтобы продолжить», без кавычек и обратных апострофов: по ней GigaCode подставляет команду в строку ввода.

## Проверки

Ошибки:
- обязательные разделы документов;
- формат и уникальность номеров;
- у каждого FR есть пример и основание; основание — существующее решение `D-…`, не помеченное как заменённое;
- цели ссылок существуют; для ссылки в тупик указывается, где она стоит;
- у открытого вопроса заполнены этап, блокировка и помощь, у решённого — ответ и решение `D-…`, ссылающееся на него, у вопроса «не входит» — ответ и упоминание в «Не входит в задачу»;
- у замечания допустимые важность и решение;
- строка статуса `spec.md` одного из двух допустимых видов: «Статус: черновик» или «Статус: одобрено <дата> · <сумма>».

Несовпадение суммы одобрения ошибкой проверки не считается: это условие перехода «Одобрено, сумма не совпадает», и снять его можно только оценкой разницы.

Условия одобрения по FR-21:
- нет открытых вопросов;
- у блокирующих замечаний последнего раздела `review.md` есть решение, и это не «отложено»;
- ошибок проверок нет.

Предупреждение: в `spec.md` больше 10 000 знаков. Считаются только буквы и цифры: пробелы, табуляция, переносы строк, знаки препинания и разметка Markdown не учитываются. Предупреждение не мешает проверкам и одобрению: его задача — заметить разросшийся документ, а не остановить работу на 10 001 знаке.

## Сейчас не делаем

- Пишущие действия сверх `link` — до ручного прогона.
- Передачу правила именования папок через контекст пользователя.
- Случай, когда одобренной версии нет в истории git.
- Напоминание о коммите после одобрения.

## Известные риски

- Английский текст `grilling` при русском общении может увести ответы модели на английский.
- Правило «каждый поиск фактов — отдельным агентом» может оказаться тяжёлым для простой задачи.

## Блоки реализации

По одному PR на блок.

1. Манифест, MCP-сервер с пустыми `status`, `check` и `link`, правила с образцами, тесты обмена с MCP-сервером.
2. `status`: выбор задачи, проверка имени папки, этап и следующий шаг, проверка источников, задание на изучение. `check` для `_work/context.md`.
3. `check` для `brainstorming.md` и `questions.md`: формат, номера, блокирующие вопросы, следующие свободные номера. Скилл `sf-grill` с `grilling`.
4. `check` для `spec.md`: пример и основание FR, заменённые основания, ссылки, размер, строка статуса и приведение текста перед подсчётом суммы, условия одобрения. `link`. Скилл `sf-spec`.
5. `check` для `review.md`. Скилл `sf-review`.
6. Изменение после одобрения через git, список зависящих FR. Скилл `sf-note`.
7. Ручной прогон проверочных ситуаций в GigaCode CLI на трёх моделях. По его итогам — решение о пишущих действиях.
