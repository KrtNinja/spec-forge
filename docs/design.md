# Устройство расширения Spec Forge

Черновик проектирования по [продуктовым требованиям](product-requirements.md). Требования остаются единственным источником поведения. Этот документ описывает, как их выполнить. Реализация не начата и требует отдельного поручения владельца.

Разделы помечены так:
- **Решено** — согласовано с владельцем.
- **Предложено** — ждёт обсуждения.

## Путь

идея → `sf-grill` → `brainstorming.md` → `sf-spec` → `spec.md` → необязательный `sf-review` → одобрение.

Открытые вопросы ведутся в `questions.md`. Новые сведения поступают через `sf-note`. Временные материалы лежат в `_work/`.

## Состав и подключение

**Предложено.**

```
gigacode-extension.json    имя, contextFileName → rules/spec-forge.md,
                           mcpServers.spec-forge → node ${extensionPath}/server/mcp.mjs
rules/spec-forge.md        общие правила, около 1 КБ
skills/sf-grill/SKILL.md    вместе с текстом grilling; рядом LICENSE-grilling
skills/sf-spec/SKILL.md
skills/sf-review/SKILL.md
skills/sf-note/SKILL.md
server/                    MCP-сервер и логика без зависимостей
tools/                     проверки разработки, как сейчас
```

Подключение: `gigacode extensions link <папка расширения>`. MCP-сервер работает по stdio без npm-пакетов: пользователю ничего устанавливать не нужно, а путь к скрипту не попадает в shell-команды агента.

**Решено:** команд четыре — `sf-grill`, `sf-spec`, `sf-review`, `sf-note`. Отдельных команд «продолжить» и «одобрить» нет:
- любой скилл на входе запрашивает у инструмента состояние и продолжает с нужного места;
- ответ бизнеса или разработчика приходит через `sf-note`;
- одобрение выбирается вариантом из ответа инструмента.

Скиллы доступны модели для вызова. Это нужно, чтобы продолжить в текущей сессии по FR-13 и распознать новые сведения по FR-24.

## Детерминированный инструмент

**Предложено:** один MCP-инструмент `spec_forge` с полем `action`.

| action | Что делает |
|---|---|
| `status` | Находит задачу: явно указанную, единственную начатую или просит выбрать. Определяет этап и доступные действия, возвращает короткий текст для пользователя и следующий шаг для агента |
| `start` | Проверяет имя папки, предложенное агентом, и создаёт заготовки документов |
| `save` | Записывает список записей (решения, вопросы, ответы, решения по замечаниям) и повторяет проверки |
| `check` | Нумерует `FR-?`, проставляет однозначные ссылки, проверяет структуру и цели ссылок |
| `approve` | Проверяет условия FR-21 и ставит отметку об одобрении |
| `assess` | Принимает оценку агента «смысл изменился: да/нет» после правки одобренного документа |

**Решено:** записи пишет инструмент через `save`. В GigaCode вызов MCP достаточно разрешить один раз на сессию. Решения из одного блока ответов сохраняются одним вызовом. Агент сам пишет только текст FR в `spec.md`, а затем вызывает `check`. Поэтому правила разметки записей в скиллы не попадают.

Ответ инструмента — обычный русский текст: что показать пользователю и что сделать дальше. Отдельная грамматика служебных строк, как в sdd-planner, не нужна.

## Документы задачи

**Решено:** папка задачи — `docs/<имя>/`. `status` считает начатыми задачами только папки `docs/*/`, в которых есть `brainstorming.md`.

**Решено:** номера записей латиницей — `FR`, `D` (решение), `Q` (вопрос), `R` (замечание проверки). Причина: кириллическая «Р» и латинская «P» выглядят одинаково, и модель их путает. Заголовки и текст пишутся по-русски.

**Предложено:**

| Файл | Содержимое |
|---|---|
| `brainstorming.md` | Запрос, источники, решения `D-01…` (слова пользователя отдельно от рекомендации агента), «Не входит в задачу» |
| `questions.md` | `Q-01…`: этап, блокирует (да/нет), чья помощь нужна, статус (открыт / решён / не входит), ответ |
| `spec.md` | Строка статуса, цель, `FR-01…` (поведение, пример, «Основание: [D-03](brainstorming.md#d-03)»), границы, ссылка на `questions.md` |
| `_work/review.md` | Разделы проверок; в разделе `R-01…`: важность, где, проблема, рекомендация, решение. Учитывается последний раздел |
| `_work/context.md` | Результат изучения источников, свободный текст |

Шаблоны живут в коде инструмента: `start` создаёт заготовки, и шаблон не попадает в контекст модели.

## Состояние и переходы

**Предложено:** отдельного файла состояния нет, этап вычисляется из документов.

| Условие | Доступный шаг |
|---|---|
| Нет папки задачи | Новая задача |
| Есть `brainstorming.md`, нет `spec.md` | Продолжить обсуждение. Если блокирующих вопросов нет — подготовить требования |
| Есть `spec.md`, проверки не пройдены | Исправить |
| Проверки пройдены | Проверить требования (рекомендуется) или одобрить, если условия выполнены |
| В последнем разделе `review.md` есть блокирующее замечание без решения | Разбор замечаний |
| Одобрено, `spec.md` изменился | Оценка `assess`: правка без смены смысла или повторное одобрение |

**Решено:** одобрение хранится строкой в `spec.md`: «Статус: одобрено 2026-11-06 · a1b2c3». Последняя часть — короткая контрольная сумма содержимого без строки статуса. Дословные слова пользователя не записываются.

**Предложено:** разницу после одобрения даёт git. Если сумма не совпадает, инструмент ищет в истории `spec.md` последний коммит с этой же отметкой одобрения и передаёт агенту разницу с ним. По этой разнице агент оценивает смысл через `assess`.

Если коммита с одобренной версией нет (одобрили и изменили до коммита) или папка не в git, сравнивать не с чем. В этом случае требуется повторное одобрение без оценки.

## Контекст

**Предложено:**
- **Всегда загружено** (`rules/spec-forge.md`, около 1 КБ): правило языка; работа идёт через `spec_forge`, а если его не видно — поиск инструментов (FR-28); решения принимает пользователь; записи инструмента вручную не править.
- **По вызову**: тело текущего скилла и ответ инструмента со следующим шагом.

## sf-grill и grilling

**Решено:** вопросы задаются блоками до 4 через инструмент выбора. Вариантов 2–4, рекомендуемый первым. Контекст длиннее двух фраз даётся коротким сообщением перед блоком. Если инструмента выбора нет — нумерованный список.

**Решено:** вместо справочника тем в `sf-grill` одна строка с шестью сторонами FR из FR-03: участники, действия, условия, бизнес-правила, результаты, существенные исключения. По ней агент проверяет, что раскрыто; анкетой она не служит. Отдельный файл с примерами вопросов — только если одной строки окажется мало.

**Решено:** берём исходный `grilling` и правим в нём только конфликты с процессом. Логика раундов сохраняется: раунд — весь фронт вопросов, обсуждение заканчивается, когда фронт пуст. Правки:
- раунд показывается блоками до 4 вопросов;
- вопрос без ответа уходит в `questions.md` и считается пройденной веткой; независимые ветки продолжаются;
- завершение — фраза FR-12 вместо подтверждения общего понимания.

Исходный текст английский, правки минимальные. Источник, коммит и список правок указываются в `skills/sf-grill/LICENSE-grilling`.

**Решено временно:** адаптированный текст `grilling` записан прямо в `sf-grill/SKILL.md`. Это не требует лишнего вызова, вывода на экран или прав на чтение папки расширения. Объём контекста — около 2 КБ при входе в скилл.

Папки `external-skills/` нет. Условия MIT требуют, чтобы уведомление об авторстве и текст лицензии сопровождали копию. Поэтому они лежат в `skills/sf-grill/LICENSE-grilling`, вместе с источником и списком правок. В контекст модели этот файл не загружается.

Это отступление от FR-06, где указано размещение в `external-skills/grilling`. К вопросу владелец вернётся позже. До этого FR-06 не меняется.

Рассмотренные варианты:
- Возврат текста через ответ инструмента не подходит: пользователь видит его на экране целиком.
- Чтение файла по пути зависит от прав GigaCode и от знания пути установки.
- Встраивание при сборке со сверкой в `tools/` остаётся кандидатом на потом.

## Изучение источников

**Решено:** изучение источников всегда выполняет отдельный агент, независимо от объёма. Источников нет — изучения нет. Отдельный агент недоступен — действует FR-26: пользователь выбирает другое окно или явно подтверждает продолжение здесь.

**Решено:** задание собирает инструмент из заготовки: папка задачи, список источников, куда и в каком виде записать результат. Агент добавляет только то, что нужно выяснить. Одно и то же задание подходит и для отдельного агента, и для другого окна. Для другого окна пользователь получает готовую команду.

**Решено, пробуем:** `_work/context.md` состоит из трёх разделов:
- «Факты» — каждый с источником;
- «Противоречия»;
- «Не найдено».

Инструмент проверяет, что файл есть и разделы на месте. Смысл фактов он не оценивает.

## sf-spec

**Решено:** у каждого FR есть хотя бы один пример. Инструмент проверяет только наличие примера, смысл оценивает агент.

**Решено:** основание FR — только решение `D-…`. Когда пользователь отвечает на вопрос `Q-…`, инструмент при `save` сам создаёт решение `D-…` со ссылкой на этот вопрос.

## sf-review и разбор замечаний

**Решено:** проверяющий агент передаёт замечания списком через `save`. Инструмент сам оформляет новый раздел `_work/review.md` и присваивает номера `R-…`.

Исходим из того, что отдельный агент в GigaCode может вызывать MCP-инструменты расширения. Это подтверждается ручным прогоном.

**Решено:** два уровня важности — «блокирует» и «замечание».

**Решено:** если пользователь принял рекомендацию или дал своё решение, и это меняет поведение, инструмент создаёт решение `D-…` со ссылкой на `R-…`. Правка формулировки без смены поведения меняет только FR, новое `D` не создаётся. Меняется ли поведение, определяет агент.

## Переходы между сессиями

**Решено:** новая сессия в GigaCode — это `/clear` или перезапуск окна. Инструмент показывает оба способа и команду продолжения, например `/sf-spec <имя>`. Последняя строка ответа — «Tip: Введите /sf-spec <имя> чтобы продолжить», без кавычек и обратных апострофов: по ней GigaCode подставляет команду в строку ввода.

## Проверки

**Предложено:**
- обязательные разделы документов;
- формат и уникальность номеров;
- у каждого FR есть пример и основание, и основание — существующее решение `D-…`;
- цели ссылок существуют, место ссылки в тупик указывается;
- у открытого вопроса заполнены этап, блокировка и помощь, у решённого есть ответ;
- допустимые значения решений по замечаниям;
- контрольная сумма одобрения.

## Блоки реализации

**Предложено:** по одному PR на блок.

1. Манифест, пустой MCP-сервер, rules, тесты протокола.
2. `status` и `start`: выбор задачи, имя папки, заготовки.
3. `questions.md` и логика блокировки.
4. `brainstorming.md`, `sf-grill`, подключение `grilling`.
5. `spec.md`, нумерация, ссылки, `check`, `sf-spec`.
6. `review.md`, `sf-review`, разбор замечаний.
7. `approve`, `assess`, `sf-note`.
8. Ручной прогон проверочных ситуаций в GigaCode CLI на трёх моделях.
