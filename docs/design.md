# Устройство расширения Spec Forge

Черновик проектирования по [продуктовым требованиям](product-requirements.md). Требования остаются единственным источником поведения. Этот документ описывает, как их выполнить. Реализация не начата и требует отдельного поручения владельца.

Разделы помечены так:
- **Решено** — согласовано с владельцем.
- **Предложено** — ждёт обсуждения.

## Путь

идея → `sf-grill` → `brainstorming.md` → `sf-spec` → `spec.md` → необязательный `sf-review` → одобрение.

Открытые вопросы ведутся в `questions.md`. Новые сведения поступают через `sf-note`. Временные материалы лежат в `_work/`.

## Состав и подключение

**Предложено.**

```
gigacode-extension.json    имя, mcpServers.spec-forge → node ${extensionPath}/server/mcp.mjs
rules/spec-forge.md        общие правила и образцы D/Q, около 1,5 КБ, paths: **/docs/**
skills/sf-grill/SKILL.md    вместе с текстом grilling; рядом LICENSE-grilling
skills/sf-spec/SKILL.md
skills/sf-review/SKILL.md
skills/sf-note/SKILL.md
server/                    MCP-сервер и логика без зависимостей
tools/                     проверки разработки, как сейчас
```

Подключение: `gigacode extensions link <папка расширения>`. MCP-сервер работает по stdio без npm-пакетов: пользователю ничего устанавливать не нужно, а путь к скрипту не попадает в shell-команды агента.

**Решено:** команд четыре — `sf-grill`, `sf-spec`, `sf-review`, `sf-note`. Отдельных команд «продолжить» и «одобрить» нет:
- любой скилл на входе запрашивает у инструмента состояние и продолжает с нужного места;
- ответ бизнеса или разработчика приходит через `sf-note`;
- одобрение выбирается вариантом из ответа инструмента.

Скиллы доступны модели для вызова. Это нужно, чтобы продолжить в текущей сессии по FR-13 и распознать новые сведения по FR-24.

## Детерминированный инструмент

**Решено: сначала минимум записи.** Инструмент начинает с трёх действий. Два только читают, третье пишет только ссылки. Записи и документы ведёт модель по коротким образцам. Пишущие действия добавляются только там, где ручной прогон в GigaCode покажет реальные ошибки модели. Так кода на старте меньше, и сложность растёт по наблюдаемым ошибкам, а не на всякий случай.

Один MCP-инструмент `spec_forge` с полем `action`:

| action | Что делает |
|---|---|
| `status` | Находит задачу: явно указанную, единственную подходящую или просит выбрать. Проверяет имя новой папки. Определяет этап, доступные действия и следующий шаг. Если переданы источники, выдаёт задание на их изучение |
| `check` | Проверяет документы задачи: структуру, номера, ссылки, условия одобрения. Подсказывает следующие свободные номера. Если переданы затронутые решения, возвращает зависящие от них FR. Когда условия одобрения выполнены, выдаёт готовую строку статуса для `spec.md`. Ничего не меняет |
| `link` | Превращает номера `D-…`, `Q-…`, `R-…`, `FR-…` без ссылки в ссылки с правильным файлом, путём и якорем. Чинит ссылку с ошибочной целью, если цель однозначна, а неоднозначную только показывает. Больше ничего не меняет |

**Решено: у каждого действия одна ответственность.** `check` не исправляет документы, `link` не проверяет ничего, кроме ссылок. Новая обязанность — новое действие, и только вместе с правкой этого документа.

Модель пишет только номер, например «Основание: D-03». Что на что ссылается, решает она. Оформление ссылки — работа `link` по FR-25. Номера не переиспользуются, а файлы не переезжают, поэтому готовые ссылки не устаревают. Если решение заменено, `check` укажет FR, которые на него опираются. Перевод FR на новое решение — смысловая правка модели.

Отложено до результатов прогона: `save` (запись решений, вопросов и замечаний), `start` (заготовки документов), запись одобрения инструментом. Это заменяет прежнее решение, по которому записи писал инструмент.

Разрешить вызов MCP в GigaCode достаточно один раз на сессию.

### Ответ инструмента

**Решено:** пользователь видит ответ инструмента целиком, поэтому ответ пишется для человека. Указание агенту формулируется так, чтобы и человеку было понятно, например «Дальше: вопросы по оставшимся темам». JSON и служебной грамматики, как в sdd-planner, нет.

Объём ответа:
- `check` без ошибок — одна строка: «Ошибок нет. Следующие номера: D-06, Q-03.»;
- ошибки — список «где — что»;
- `status` — 2–4 строки: задача, этап, что дальше;
- разница после одобрения показывается как есть: пользователю полезно видеть, что изменилось.

Оформление в Markdown:
- абзацы и блоки разделяются пустой строкой — одиночный перенос строки склеивает текст в сплошной абзац;
- перечни начинаются с «- », каждый пункт на своей строке;
- команды, имена файлов и номера записей пишутся в обратных апострофах;
- заголовок блока выделяется жирным на отдельной строке;
- строка «Tip: Введите … чтобы продолжить» идёт последней и без оформления.

Агент не пересказывает ответ инструмента: пользователь его уже видел. Это одна строка в rules.

## Документы задачи

**Решено:** папка задачи — `docs/<имя>/`. `status` считает начатыми задачами только папки `docs/*/`, в которых есть `brainstorming.md`.

**Решено:** номера записей латиницей — `FR`, `D` (решение), `Q` (вопрос), `R` (замечание проверки). Причина: кириллическая «Р» и латинская «P» выглядят одинаково, и модель их путает. Заголовки и текст пишутся по-русски.

**Предложено:**

| Файл | Содержимое |
|---|---|
| `brainstorming.md` | Запрос, источники, решения `D-01…` (слова пользователя отдельно от рекомендации агента), «Не входит в задачу» |
| `questions.md` | `Q-01…`: этап, блокирует (да/нет), чья помощь нужна, статус (открыт / решён / не входит), ответ |
| `spec.md` | Строка статуса, цель, `FR-01…` (поведение, пример, «Основание: [D-03](brainstorming.md#d-03)»), границы, ссылка на `questions.md` |
| `_work/review.md` | Разделы проверок; в разделе `R-01…`: важность, где, проблема, рекомендация, решение. Учитывается последний раздел |
| `_work/context.md` | Результат изучения источников, свободный текст |

**Предложено: где лежат образцы.** Документы создаёт и дополняет модель по образцам, а ошибки формата ловит `check`.
- Образцы записи решения `D-…` и вопроса `Q-…` — в `rules/spec-forge.md`: их пишут несколько скиллов.
- Образец FR — только в `sf-spec`.
- Образец замечания `R-…` — только в `sf-review`.
- Порядок разделов документа задаёт образец, а не отдельный шаблон.

## Состояние и переходы

**Предложено:** отдельного файла состояния нет, этап вычисляется из документов.

| Условие | Доступный шаг |
|---|---|
| Нет папки задачи | Новая задача |
| Есть `brainstorming.md`, нет `spec.md` | Продолжить обсуждение. Если блокирующих вопросов нет — подготовить требования |
| Есть `spec.md`, проверки не пройдены | Исправить |
| Проверки пройдены | Проверить требования (рекомендуется) или одобрить, если условия выполнены |
| В последнем разделе `review.md` есть блокирующее замечание без решения | Разбор замечаний |
| Одобрено, `spec.md` изменился | Агент оценивает разницу: правка без смены смысла или повторное одобрение |

**Решено:** одобрение хранится строкой в `spec.md`: «Статус: одобрено 2026-11-06 · a1b2c3». Последняя часть — короткая контрольная сумма содержимого без строки статуса. Дословные слова пользователя не записываются. Модель не вычисляет сумму сама: после явного решения пользователя она вставляет строку, которую выдал `check`.

**Решено:** разницу после одобрения даёт git. Если сумма не совпадает, инструмент ищет в истории `spec.md` последний коммит с этой же отметкой одобрения и передаёт агенту разницу с ним. По этой разнице агент оценивает смысл. Смысл не изменился — агент вставляет новую строку статуса из `check` с прежней датой одобрения. Изменился — ставит «Статус: не одобрено», и требуется повторное одобрение.

Случай, когда одобренной версии нет в истории git, пока не учитывается.

## Контекст

**Предложено:**
- **Общие правила** (`rules/spec-forge.md`, около 1,5 КБ вместе с образцами): правило языка; работа идёт через `spec_forge`, а если его не видно — поиск инструментов (FR-28); решения принимает пользователь; после правки документов вызвать `link`, затем `check`; ответ инструмента не пересказывать; образцы записей `D-…` и `Q-…`.

  **Решено:** правила подключаются не через `contextFileName`, а заголовком `paths: ["**/docs/**"]` в начале файла, как предлагает GigaCode. Тогда они загружаются только при работе с документацией, а не во всех сессиях. Чтобы правила были в контексте до первого ответа, первый шаг каждого скилла после `status` — прочитать документы задачи: `brainstorming.md`, затем `spec.md` и `_work/context.md`, если они есть. Они нужны и для продолжения работы. В новой задаче документов ещё нет, и правила подгружаются, когда агент создаёт `brainstorming.md`.
- **По вызову**: тело текущего скилла и ответ инструмента со следующим шагом.

## sf-grill и grilling

**Решено:** вопросы задаются блоками до 4 через инструмент выбора. Вариантов 2–4, рекомендуемый первым. Контекст длиннее двух фраз даётся коротким сообщением перед блоком. Если инструмента выбора нет — нумерованный список.

**Решено:** вместо справочника тем в `sf-grill` одна строка с шестью сторонами FR из FR-03: участники, действия, условия, бизнес-правила, результаты, существенные исключения. По ней агент проверяет, что раскрыто; анкетой она не служит. Отдельный файл с примерами вопросов — только если одной строки окажется мало.

**Решено:** берём исходный `grilling` и правим в нём только конфликты с процессом. Логика раундов сохраняется: раунд — весь фронт вопросов, обсуждение заканчивается, когда фронт пуст. Правки:
- раунд показывается блоками до 4 вопросов;
- вопрос без ответа уходит в `questions.md` и считается пройденной веткой; независимые ветки продолжаются;
- завершение — фраза FR-12 вместо подтверждения общего понимания.

Текст остаётся английским и не переводится. Правки — только перечисленные выше. Источник, коммит и список правок указываются в `skills/sf-grill/LICENSE-grilling`.

**Решено:** текст `grilling` на языке оригинала, без перевода, записан прямо в `skills/sf-grill/SKILL.md`. Лишнего вызова нет, на экран ничего не выводится, права на чтение папки расширения не нужны. Объём контекста — около 2 КБ при входе в скилл.

**Решено:** текст `grilling` стоит в `SKILL.md` одним куском между служебными строками:

```
<!-- grilling: начало (MIT, см. LICENSE-grilling) -->
…
<!-- grilling: конец -->
```

Правила `sf-grill` находятся только вне этих строк. Чтобы убрать `grilling`, удаляется кусок между ними вместе с самими строками.

Рядом лежит `skills/sf-grill/LICENSE-grilling`: условия MIT требуют, чтобы уведомление об авторстве и текст лицензии сопровождали копию. В том же файле указаны источник, коммит и список правок. В контекст модели он не загружается.

Отклонённые варианты:
- Возврат текста через ответ инструмента: пользователь видит его на экране целиком.
- Чтение файла по пути: зависит от прав GigaCode и от того, знает ли модель путь установки.

## Изучение источников

**Решено:** изучение источников всегда выполняет отдельный агент, независимо от объёма. Источников нет — изучения нет. Отдельный агент недоступен — действует FR-26: пользователь выбирает другое окно или явно подтверждает продолжение здесь.

**Решено:** задание выдаёт `status` по заготовке, когда ему переданы источники: папка задачи, список источников, куда и в каком виде записать результат. Агент добавляет только то, что нужно выяснить. Одно и то же задание подходит и для отдельного агента, и для другого окна. Для другого окна пользователь получает готовую команду.

**Решено, пробуем:** `_work/context.md` состоит из трёх разделов:
- «Факты» — каждый с источником;
- «Противоречия»;
- «Не найдено».

`check` проверяет, что файл есть и разделы на месте. Смысл фактов он не оценивает.

## sf-spec

**Решено:** у каждого FR есть хотя бы один пример. Инструмент проверяет только наличие примера, смысл оценивает агент.

**Решено:** основание FR — только решение `D-…`. Когда пользователь отвечает на вопрос `Q-…`, агент записывает решение `D-…` со ссылкой на этот вопрос. `check` проверяет, что у решённого вопроса есть такое решение.

## sf-review и разбор замечаний

**Решено:** проверяющий агент сам дописывает новый раздел в `_work/review.md` по образцу из `sf-review`, затем вызывает `check`. Исходим из того, что отдельный агент в GigaCode может вызывать MCP-инструменты расширения.

**Решено:** два уровня важности — «блокирует» и «замечание».

**Решено:** если пользователь принял рекомендацию или дал своё решение, и это меняет поведение, агент записывает решение `D-…` со ссылкой на `R-…`. Правка формулировки без смены поведения меняет только FR, новое `D` не создаётся. Меняется ли поведение, определяет агент.

## Вход в работу и выбор задачи

**Решено:** указана ли задача в команде или это описание идеи, определяет модель. Инструмент проверяет, что названная задача существует.

**Решено:** `/sf-grill` без аргументов при одной начатой задаче продолжает её. В первом ответе видны имя задачи и вариант «Начать новую задачу». Для `/sf-spec`, `/sf-review` и `/sf-note` подходящая задача — та, где эта команда сейчас доступна.

**Решено:** имя папки новой задачи спрашивается у пользователя: в команде может быть принято своё правило, например `JIRA-555`. Варианты ответа:
- своё имя;
- имя, которое предложил агент: латиница строчными буквами через дефис, например `order-search`.

Если пользователь дал имя кириллицей, его просят написать латиницей. `status` допускает латинские буквы, цифры и дефис и проверяет, что папки с таким именем нет. Папку и `brainstorming.md` создаёт агент. Передачу правила именования через контекст пользователя добавим позже.

## sf-note

**Решено:** агент по смыслу называет решения `D-…` и вопросы `Q-…`, которых касаются новые сведения. Инструмент по ссылкам «Основание» возвращает список FR, которые от них зависят. Отдельного действия для этого нет: список приходит в ответе `check`, если ему переданы затронутые записи. Разбор ссылок инструмент и так выполняет для проверок, поэтому обратный список почти ничего не стоит.

**Решено:** если новые сведения меняют или добавляют решение, агент записывает новое `D-…`. Прежнее решение не удаляется, а получает отметку «заменено D-…» — так сохраняется история. Ответ на открытый вопрос оформляется так же, как в sf-spec: через новое решение `D-…`.

## Переходы между сессиями

**Решено:** новая сессия в GigaCode — это `/clear` или перезапуск окна. Инструмент показывает оба способа и команду продолжения, например `/sf-spec <имя>`. Последняя строка ответа — «Tip: Введите /sf-spec <имя> чтобы продолжить», без кавычек и обратных апострофов: по ней GigaCode подставляет команду в строку ввода.

## Проверки

**Предложено:**
- обязательные разделы документов;
- формат и уникальность номеров;
- у каждого FR есть пример и основание, и основание — существующее решение `D-…`, не отмеченное как заменённое;
- цели ссылок существуют, место ссылки в тупик указывается;
- у открытого вопроса заполнены этап, блокировка и помощь, у решённого есть ответ;
- допустимые значения решений по замечаниям;
- контрольная сумма одобрения;
- у решённого вопроса есть решение `D-…`, ссылающееся на него.

**Решено:** в `spec.md` не больше 10 000 знаков. Считаются только буквы и цифры: пробелы, табуляция, переносы строк, знаки препинания и разметка Markdown не учитываются. Превышение — предупреждение, а не ошибка: оно не мешает проверкам и одобрению. Задача предупреждения — заметить разросшийся документ, а не остановить работу на 10 001 знаке.

## Блоки реализации

**Предложено:** по одному PR на блок.

1. Манифест, MCP-сервер с пустыми `status`, `check` и `link`, rules с образцами, тесты протокола.
2. `status`: выбор задачи, проверка имени папки, этап и следующий шаг, задание на изучение источников.
3. `check` для `brainstorming.md` и `questions.md`: формат, номера, блокирующие вопросы. Скилл `sf-grill` с `grilling`.
4. `check` для `spec.md`: пример и основание FR, ссылки, размер, строка статуса. `link`. Скилл `sf-spec`.
5. `check` для `review.md`. Скилл `sf-review`.
6. Изменение после одобрения через git, обратный список FR. Скилл `sf-note`.
7. Ручной прогон проверочных ситуаций в GigaCode CLI на трёх моделях. По его итогам — решение о пишущих действиях.
