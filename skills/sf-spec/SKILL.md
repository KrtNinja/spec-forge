# sf-spec — подготовка требований

Сначала вызови `spec_forge` с действием `status` и командой `sf-spec`; имя задачи после `/spec-forge:sf-spec` передай в `task`. Не видишь `spec_forge` — найди его поиском инструментов, пробуя разные запросы.

Перед первым вопросом прочитай [правила Spec Forge](../../rules/spec-forge.md), если их ещё нет в контексте.

Задача выбрана — прочитай её `brainstorming.md`, `questions.md` и `spec.md`, если они есть, и действуй по ответу `status`.

## Требования

- Требования выводи только из «Решений» `brainstorming.md`. Рекомендация без решения пользователя, решение с «Заменено» и раздел «Технические детали» основанием не служат.
- Близкие правила одной темы объединяй в одну запись `FR-…` по образцу ниже: короткое название и что видит и делает пользователь, одним-двумя предложениями; «Основание» — номера решений, из которых правило выведено. В названии — только буквы, цифры, пробелы и дефис, слова — через один пробел.
- Пример добавляй, только если правило без него можно понять двояко или пользователь попросил: конкретный исход одной строкой, цитатой между правилом и основанием.
- Темы выделяй по необходимости заголовками третьего уровня, записи FR всегда пиши на четвёртом. Внутри темы сначала основное поведение, затем исключения.
- Не пиши о коде: ни путей и файлов, ни классов и методов. В `brainstorming.md` и `_work/` ссылки на код уместны, в `spec.md` — нет.
- «Не входит в задачу» — из одноимённого раздела `brainstorming.md`.
- Для правила не хватает решения — не додумывай. Пробел вне границы бизнес-требований из правил Spec Forge вопросом `Q-…` не записывай. Остальные запиши с «Этап: sf-spec»: блокирующий обсуди сразу, неблокирующий оставь открытым и продолжай.

## Образец spec.md

```markdown
# Поиск заказа по номеру

Статус: черновик

## Цель

Покупатель находит свой заказ по номеру из письма, не листая историю заказов.

## Требования

### Поиск

#### `FR-01` Поиск по полному номеру

Покупатель вводит `полный номер` заказа и видит карточку `своего` заказа.

<sub><sup>Основание: D-01</sup></sub>

#### `FR-02` Чужой и несуществующий заказ

Чужой и несуществующий заказ выглядят одинаково: сообщение `Заказ не найден`.

> Пример: Борис вводит 10234 — «Заказ не найден»; Анна вводит 99999 — то же сообщение

<sub><sup>Основание: D-03, D-04</sup></sub>

## Не входит в задачу

- Поиск в админке

## Вопросы

Открытые вопросы и ответы — в [questions.md](questions.md).
```

Раздел «Вопросы» — только если есть `questions.md`.

## Проверка и одобрение

- `check` без ошибок — вызови `status` и задай вопрос с вариантами из его ответа.
- Пользователь выбрал проверку требований или `status` ведёт к разбору замечаний — запусти скилл `sf-review` в этой сессии: путь проверки он выберет сам.
- «Одобрить» — по инструкции из последнего ответа `check`.
